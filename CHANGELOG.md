# Changelog

All notable changes to plan-runner are documented here. Versions follow [Semantic Versioning](https://semver.org/).

## 2.2.0 - 2026-09-01

Local-endpoint HTTP dispatch: `dev` and `test-author` tasks can now be served directly by a local or proxied model, without a host subagent in the loop.

- **HTTP endpoint dispatch for dev and test-author roles.** `models.endpoint.roles` (e.g. `roles: [dev, test-author]`) names which pipeline roles this run dispatches by issuing an OpenAI-compatible chat-completions request to `models.endpoint.base_url` directly, shelling out to `curl` (never Node's `fetch`), instead of handing the work to a host subagent. Only `dev` and `test-author` are eligible -- naming `analyzer`, `aggregator`, or `verifier` is a configuration error that stops the run before dispatching anything, because none of the three needs repository or tool access an HTTP completion cannot supply. A missing or non-executable `curl` is a named preflight failure, never silently retried. Preflight prints the resolved endpoint role map so a run's actual dispatch mechanism is never a silent surprise.
- **A new dispatch driver and fenced-block parser (`scripts/http-dispatch.js`, `scripts/fenced-blocks.js`).** The driver composes the chat-completions body (a 240-second default timeout under the ~300s gateway bound, and `chat_template_kwargs: {enable_thinking: false}`, both overridable through the new `models.endpoint.request` passthrough), retries exactly once at a reduced completion budget on any failure -- a timeout, a non-2xx response, no parsable fenced block, or a block truncated mid-file -- and writes only in-scope files to disk itself via the parser, which refuses any block naming a path outside the task's `owned_files`. A still-failing retry is a durable `BLOCKED`; an endpoint-bound role is never rerouted to a host subagent or a hosted model on any failure path, because degrading it would move source code off the operator's machine.
- **No self-authored return JSON.** An endpoint-bound agent is never asked to return JSON itself -- plan-runner constructs its dev-return object from the response record directly (`status`, `files_written`, `concerns`, `summary`, `token_usage`), so nothing the model claims about its own status is trusted. Its work is still graded by an independent, host-dispatched verifier exactly like any other dev agent in the wave; `models.endpoint.roles` cannot name `verifier`.
- **Bounded, read-only conventions sample.** The orchestrator composes an endpoint-bound request's read-only context from the repo's existing test files nearest the task's owned paths -- at most 3 whole files totalling at most 32 KB, nearest-first, dropping rather than truncating any file that would cross either cap. The 32 KB figure is a request-size guard, not a context-window guarantee. An empty sample is reported in the composed message and on the dispatch line rather than silently omitted.
- **Durable dispatch-mechanism recording.** `manifest.schema.json` gains `dispatch_mechanism` (`"endpoint"` | `"host_subagent"`) per agent and a `"http_usage"` `token_usage.source` for the authoritative usage object an endpoint response returns; `run-state.schema.json` gains `model_policy.endpoint.roles` and `model_policy.dispatch_by_role` so a rehydrated run still knows which roles are endpoint-bound. All new fields are optional; manifests and run-state written before 2.2.0 still validate.
- README documents the `models.endpoint.roles` list, the eligible-role set, the `models.endpoint.request` passthrough, and the endpoint role map console line.
## 2.1.1 - 2026-08-31

Pre-flight reads `.plan-runner.yml` once, and can no longer mistake it for absent.

- **A single canonical config load (Step 1a-minus-bis).** Every invocation -- fresh run and explicit `--resume` alike -- now reads the repo-root `.plan-runner.yml` once, before any setting resolves, into `config_text` / `config_present`. The six settings that used to each re-read the file for themselves (`verification.mode`, `verification.pipelined`, the `phasing` block, `agents.project`, the `models` block, `execution.mode`) extract their keys from that loaded text instead. Single-key extraction is unchanged: still no YAML parser required.
- **Absence is only ever a not-found read.** The skill now states that the file counts as absent only when the Read tool itself reports it missing -- never from the exit status of a directory listing, a glob that matched nothing, or a shell command that chains the read behind another (`ls docs doc documentation .docs && cat .plan-runner.yml`, whose listing exits non-zero whenever any candidate directory is missing). A false absence was silent and total: verification mode, pipelining, phasing, project-agent dispatch, model policy, and execution mode all reverted to defaults at once. The 1a-minus doc-directory scan gets the matching rule -- read the listing's output, never its exit status.
- **The load is on the console.** Pre-flight prints `Config: .plan-runner.yml loaded.`, `Config: no .plan-runner.yml at repo root -- using defaults.`, or `Config: .plan-runner.yml unreadable (<reason>) -- using defaults.`, so a misread is visible instead of showing up only as `(from default)` parentheticals. README gains a "Configuration file" section documenting the single file and those lines.

## 2.1.0 - 2026-08-30

Configurable model selection for all pipeline agents.

- **Model selection configuration.** A new `models:` block in a target repo's `.plan-runner.yml` (not the plan file) lets it assign a specific model to any of the six governed roles -- analyzer, dev, test-author, verifier, aggregator, integrator -- or to a tier (`haiku`, `sonnet`, `opus`), instead of relying solely on bundled defaults. Resolution precedence: a serving project agent's `model:` frontmatter (dev dispatch only) > the role's `.plan-runner.yml` key > the `models.tiers` entry for the role's tier > the built-in default (bundled agent `model:` frontmatter, the analyzer's structure heuristic, `recommended_model`, or `sonnet`). A configured value that is not one of the three tier words is passed to the host unmodified.
- **Endpoint declaration and non-degradable local/proxied models.** An optional `models.endpoint` object (`base_url`, `api_key_env`) declares a locally-served or proxied model. Preflight checks that the named environment variable is set and issues at most one 5-second health check for the whole run; a failed or timed-out check records the endpoint as unreachable and continues without raising -- it never blocks the pipeline. A model resolved through a configured endpoint is non-degradable: it never falls back to a hosted model, instead halting that dispatch (with the failure recorded) when the endpoint is unreachable and no structured-input facility exists to ask the operator.
- **Availability gate.** When a configured model cannot be served, plan-runner asks the operator once, before any dev agent is dispatched, whether to substitute the closest available model for the affected roles; declining resolves those roles using the pre-feature built-in defaults instead. The gate fires at most once per run. An unattended run with no structured-input facility degrades to the closest available model, prints and records the substitution, and continues rather than blocking. The analyzer also self-reports a `served_model` in its return JSON, compared against its configured model to catch an unservable model name that the endpoint preflight cannot detect on its own.
- **Durable recording.** The resolved model map, endpoint health, the operator's consent answer, and every substitution persist as an optional `model_policy` object in `run-state.json`, so a resumed or relayed phase rehydrates the policy instead of re-resolving `.plan-runner.yml` or re-asking the gate. Each agent's manifest entry gains `resolved_model` and `model_substituted` fields.
- **Kill-switch: `--no-model-config` / `models.enabled: false`.** Either the CLI flag or `models.enabled: false` in `.plan-runner.yml` skips the whole feature for the run: every role resolves exactly as it did before this feature existed, and the availability gate is never opened. Precedence: `--no-model-config` flag > `.plan-runner.yml` `models.enabled` > default (`true`).

- **Schema-fixture coverage fix.** `schemas/examples/manifest-agent-source-{valid,invalid}.json` shipped in 1.19.0 but were never added to the `CASES` list in `tests/validate_schemas.py`, so neither had ever run. Both are now registered and passing, and `agent_source`'s description carries the literal `pre-1.19.0` back-compat note the other optional fields use.

## 2.0.1 - 2026-08-29

- **PR diff uses the fetched remote base.** The pr skill now runs `git fetch origin <base>` and computes the whole-branch `Changes` summary against `origin/<base>...HEAD`, falling back (with a printed warning) to the local ref only when the fetch fails. Previously a local base branch left behind by earlier releases inflated the file and line counts with already-merged commits.

## 2.0.0 - 2026-08-29

Major release: the default execution model changes from wave barriers to a task DAG in Git repositories. Existing flags and the no-Git wave executor remain, but run-state, events, manifests, and reports are now task-oriented, so tooling that parsed 1.x wave artifacts should treat this as a breaking change.

- **Task-DAG executor (default).** Usable Git worktree checkouts now execute a dependency-ready graph of stable task IDs rather than waiting at wave barriers. Ready tasks retain the six-task concurrency ceiling, run from dependency-satisfying integration commits in disposable worktrees, and can be integrated only by the central integrator after deterministic checks and independent verification.
- **Safe fallback and recovery.** `execution.mode: wave` is the explicit rollback path, while missing Git/worktree capability automatically keeps the existing no-Git wave executor. DAG preflight requires a clean base and an explicit stash-or-abort decision for dirty worktrees; durable task state and append-only events carry branch ownership, retries, blocks, verification, and resume evidence. Phasing now checkpoints DAG execution by integration count via `phasing.max_integrations_per_phase`, retaining relay/stop behavior.
- **Task-oriented delivery evidence.** Manifests, run reports, and PR handoff expose task outcomes, ownership and retry/block evidence, and honest token coverage. A PR is created or updated for human review only; Plan Runner never gains automatic merge authority.
- **Release protocol.** The Claude and Codex manifests, package metadata, changelog, and contract-test version pin are synchronized at 2.0.0. Release smoke guidance now covers dual-client DAG behavior, ownership enforcement, task recovery, wave fallback, required validators, and human-reviewed PR delivery.

## 1.19.0 - 2026-07-26

Project-agent dispatch: dev tasks can now be served by the target repo's own agent definitions.

- **Project-agent dispatch for dev tasks.** The run skill builds an in-session inventory of project-defined agents (`.claude/agents/*.md`, `.codex/agents/*.md`, plus agent locations and explicit "use agent X for Y" routing directives named by the target repo's AGENTS.md/CLAUDE.md) and, when a dev task's domain is clearly covered by a discovered agent's description, embeds that agent's definition in the dev prompt in place of plan-dev.md's domain-guidance half -- falling back to bundled plan-dev whenever the match is doubtful. An explicit routing directive overrides the conservative description match. Agents whose `tools` frontmatter lacks both Write and Edit are disqualified with a logged reason (never widened); a selected agent's `model` frontmatter wins over the task's `recommended_model`, which remains the model for every bundled dispatch. Test-author, verifier, and aggregator dispatches always use bundled definitions regardless of inventory. `--no-project-agents` / `agents.project: false` restores byte-identical pre-feature dispatch; malformed or unreadable agent files are skipped with a logged reason, never fatal.
- **Dev Return Contract split + return validation.** `agents/plan-dev.md` is split into labeled domain-guidance and Dev Return Contract halves; every dev dispatch (bundled or project) embeds the contract, declared to override any conflicting instruction in a project agent's definition. A project-agent return that fails `dev-return.schema.json` is re-prompted once with the schema alone; a second failure records a `return_contract_violation` bug carrying the dispatch's `agent_source` and pins the task to bundled plan-dev for the next cycle, with no return field ever fabricated.
- **Provenance everywhere.** Each dev dispatch prints a "served by <agent>" line; `agent_source` (`"bundled"` | `"project:<name>"`) is recorded in the per-agent manifest entry (new optional `manifest.schema.json` field with valid/invalid fixtures; pre-1.19.0 manifests still validate), surfaces in the Run Report, and feeds a new PR-body "Agent sources" stat that is omitted entirely when manifests predate the field. README documents the feature surface and `docs/release-smoke.md` gains an adversarial-matching-agent case (conflicting output format, self-commit instruction) plus a malformed-agent-file skip case.

## 1.18.0 - 2026-07-26

Four production-found defects fixed (issues #11, #19, #20, #21; PRs #23-#26):

- **File-backed agent returns (#11).** Every dev agent and verifier dispatch prompt names a deterministic `return_file` under `$phase_dir/returns/`; the agent writes its final JSON there as its last action and the orchestrator reads that file as the source of truth. The task-result/mailbox message is now a convenience preview only -- on the teams backend it could be permanently lost to the idle-ping race (`TaskOutput` cannot resolve named background agents; a `SendMessage` resend races idle teardown), forcing spurious `UNVERIFIABLE` waves. Verifier waits poll the file (durable across idling and `TaskStop`), the stuck-teammate fallback consults it before declaring `BLOCKED`, and teardown can no longer lose a completed verdict. `agents/plan-verifier.md` gains `Write` solely for this one file, reason recorded in its rules.
- **Step 2 resolves every impl `tests_to_satisfy` path (#19).** Each path must exist on disk or appear in the `owned_files` of an earlier-wave test-author; otherwise validation fails and STOPs naming the impl agent and the unresolvable path. Closes the silent vacuous green where an invented path matched zero tests, exited 0, and recorded `PASSED` for an implementation nothing verified.
- **Step 2 enforces test-author/impl `owned_files` disjointness (#20).** A test-author sharing files with its paired impl (paired via `tests_to_satisfy`, checked across waves) fails validation naming both agents and each shared path -- previously the overlap produced a zero-test red that silently skipped the paired impl as BLOCKED (a P0 task lost). The legitimate single-file exception (a `[[bin]]`-style target unreachable from an external test file) is an explicit new optional `inline_tests: true` on the test-author node in `wave-plan.schema.json` (pre-1.18.0 wave plans omit it and still validate), capped at exactly one shared file.
- **Marketplace description rewritten to ecosystem length.** The catalog-facing `description` in `.claude-plugin/plugin.json` had accumulated a clause per release and reached ~4,200 characters -- 28x the ~150-character median across public plugin catalogs, and truncated to its first few lines on every browsing surface (`/plugin` list, claude.com/plugins cards). It is now a 255-character capability blurb; a new contract test caps it at 300 characters so it cannot re-grow, and per-release detail lives here in the CHANGELOG. The release protocol in CLAUDE.md is updated to match.
- **Invalid-green detection (#21).** The green gate parses the runner-reported executed-test count: zero tests ran records `green_run.result: "INVALID"` with the new `valid_green: false` -- never `PASSED` -- and an unparseable count records the honest `valid_green: null` for the verifier to judge from the raw output, mirroring the invalid-red rule's division of labour. `captured_test_output` leads with a `GREEN GATE TEST COUNT` line and the verifier's green-gate mode gains a first "tests must actually run" step flagging the P1. `manifest.schema.json` documents `INVALID` and the optional `valid_green` field (pre-1.18.0 manifests omit it).

## 1.16.0 - 2026-07-23

- **Late-verdict reconciliation.** An expired bounded wait for a wave verifier no longer permanently closes that wave against a verdict that shows up afterward. A verifier report arriving after its wave was already recorded `UNVERIFIABLE` or superseded by a replacement verifier is now reconciled by union of findings, and a later or replacement `CLEAN` can never erase an earlier `BUGS_FOUND`. Any aggregation, fix-plan, or PR artifacts already produced before the late verdict landed are revised to match -- including returning a PR to draft if it had already been published ready on a now-false zero-bug claim. This is what stops a wave's real verdict from being lost when a merely slow verifier gets mistaken for a dead one.
- **PR title resolves through fix-plan cycles.** The PR-opening step now follows a generated fix-plan's `**Original plan:**` line back to the true original plan (chased transitively, with a hop cap), so a feature branch that went through one or more fix cycles is titled from the original plan instead of collapsing to `fix: fix plan (cycle 2)`.
- The plan-analyzer agent may no longer invent `owned_files`, must honor a plan-declared dependency graph (`Blocked by:`) over its preferred TDD wave shape, and must not force test-author/impl roles onto non-runnable prose, docs, or config tasks.
- Generated fix-plans from the plan-aggregator agent now carry a mandated `**Original plan:**` line naming the true original plan, copied through transitively across repeated fix cycles -- the source the PR-title fix above depends on.
- `.claude-plugin/plugin.json`'s marketplace-facing `description` now documents the late-verdict reconciliation guarantee.

## 1.15.0 - 2026-07-23

- **Auto-detected output location.** Cycle artifacts now go under `<docs_base>/plan-runner/` instead of a hardcoded `docs/plan-runner/`. A new pre-flight step (Step 1a-minus, ahead of the resumable-run auto-detect, which consumes the resolved base) resolves `<docs_base>` in three tiers: (1) an explicit prose statement naming a documentation directory in the repo-root `CLAUDE.md`, then the repo-root `AGENTS.md`, then in-context repository instructions -- a vague mention of "docs" with no named directory does not count; (2) otherwise a repo-root top-level scan for a directory named literally `docs`, `doc`, `documentation`, or `.docs`, first match in that fixed order; (3) otherwise the default `docs`, which is byte-for-byte the pre-1.15.0 behavior. There is no settings key -- nothing to configure. The resolved base and its source are printed once at run start (`Output location: <docs_base>/plan-runner/ (from <CLAUDE.md | AGENTS.md | top-level scan | default>).`) and recorded as `docs_base` in the cycle manifest; manifests written before 1.15.0 omit the field and always meant `docs`. When the resolved base differs from `docs`, resume discovery globs run-states under both `<docs_base>/plan-runner/` and the legacy `docs/plan-runner/`.
- The SessionStart hook now writes the base-agnostic `**/plan-runner/` `.gitignore` entry instead of the literal `docs/plan-runner/`, so generated artifacts stay ignored wherever the base resolves.

## 1.14.0 - 2026-07-19

- **Pipelined verification (default).** The wave verifier no longer sits on the critical path between waves. Each wave now commits first (Step 4b), then dispatches its verifier against a read-only snapshot worktree pinned to that commit (Step 4c) and runs while the NEXT wave's dev agents work; the verdict is captured at the next wave's pickup or the end-of-range drain (Step 4g). At most one wave's verification is in flight, every verdict still lands before aggregation, and the honesty invariants are untouched: no self-verify, `UNVERIFIABLE` for a verdict that never lands, and the coverage gate still makes it structurally impossible to open a PR with an outstanding verdict. Kill-switch: `--sync-verify` or `verification.pipelined: false` in `.plan-runner.yml` (precedence flag > file > default `true`). No-git runs, waves with nothing to commit, and snapshot failures verify synchronously as before.
- **One full-suite run per wave.** TDD gates keep their per-agent targeted single-file runs but now run the full test command once per wave for the baseline regression diff, instead of once per gated agent (previously a wave of six gated agents re-ran a slow suite six times). Regressions outside the wave's expected reds are appended to every gated agent's captured output as a shared `WAVE SUITE REGRESSIONS` block; the verifier attributes them by owned files.
- **Commit message change.** Wave commits no longer carry a verifier-status suffix (the verdict does not exist yet at commit time); verdicts live in the bug JSON, the manifest, and the PR body. Manifest wave entries are appended at verdict capture; the run-state checkpoint still updates at the commit, so crash-recovery granularity is unchanged.
- Faster paired TDD dispatch: a paired impl agent is skipped on a mechanically-detected invalid red (tests passed, exit 0) exactly as before, but no longer waits for the red-gate verifier's syntax/collection judgment when that verdict is still in flight -- an invalid-red verdict landing later still backfills `valid_red: false` and flows the P1 bug to the fix plan.

## 1.13.0 - 2026-07-16

- **Phasing for large plans.** A sliced wave plan with more waves than `phasing.max_waves_per_phase` (default `4`) now runs as sequential phases instead of one long-lived orchestrator session, so host-process memory can be reclaimed at phase boundaries. Configurable in `.plan-runner.yml` (`phasing.enabled`, `max_waves_per_phase`, `mode`, `auto_stop_phases`, `relay_max_minutes`) or per-run via `--phase-size`, `--phase-mode`, and the `--no-phasing` kill switch; precedence is flag > file > default. Below the threshold, or with phasing disabled, nothing changes -- no phase directories, no run-state file.
- **Relay vs. stop.** `relay` mode keeps a driver session alive across phase boundaries, dispatching each phase as its own subagent and keeping only a compact per-phase summary in context; `stop` mode ends the session at each phase boundary and picks the next phase up via `--resume` in a fresh process, resetting both context and host-process heap. Only `stop` fully resets process memory.
- **Adaptive mode.** With `mode: auto` (the default), plan-runner relays while the sliced phase count is at or under `auto_stop_phases` (default `3`) and switches to `stop` above it. The Agent Teams backend always uses `stop`, since a teammate cannot spawn a nested team to lead a relay.
- **Relay guardrail.** A relay run is additionally bounded by wall time: if elapsed time since the run started exceeds `relay_max_minutes` (default `90`) at a phase boundary, plan-runner forces a stop-and-resume there instead of continuing to relay.
- **Resume and crash recovery.** Every phased run checkpoints to a `run-state.json` at the cycle root, updated after every wave. `--resume [path]` resumes a specific checkpoint, or (bare) the most recently updated resumable run found under `docs/plan-runner/**/run-state.json`. A fresh invocation auto-detects an incomplete run-state and offers to resume before starting a new run. Resume always re-enters at the last completed wave -- it never assumes partial or uncommitted work from an interrupted wave is done -- and warns (requiring confirmation) if the plan file's content hash has changed since checkpointing. Unphased runs write no run-state and are never resumable.
- **Agent return budgets.** `dev-return`, `bug-report`, and `wave-plan` free-text fields (`summary`, `concerns`, bug `title`/`evidence`/`expected`/`suggested_fix`, wave `rationale`/`complexity_signals`, etc.) now carry `maxLength` caps to bound per-agent return payload size; pre-1.13.0 artifacts without these caps still validate.
- Schemas: new `run-state.schema.json` (phase/wave checkpoint state) with matching valid/invalid fixtures.

## 1.11.0 - 2026-07-13

- **Agents bubble up their token usage.** Every pipeline agent (analyzer, dev, test-author, verifier, aggregator) now includes an optional `token_usage` self-report in its return JSON: the most recent usage figure the harness surfaced to it in-band (e.g. a token-budget system warning), or `null` when none appeared -- never an estimate. The orchestrator captures tokens from two sources in strict precedence: the completion result's usage summary (authoritative, `source: "harness"`) first, falling back to the agent's non-null self-report (`source: "self_report"`, an honest lower bound) -- the common rescue for teammates on the Agent Teams backend, whose usage is not always visible to the lead. `tokens: null` remains the outcome only when both sources are dry, so per-agent coverage improves without weakening the never-fabricate invariant.
- Schemas: `dev-return` and `wave-plan` gain an optional `token_usage` self-report field; manifest `token_usage.by_agent` entries and the reusable `tokenCount` shape gain an optional `source` enum (`harness` | `self_report`). All new fields are optional -- pre-1.11.0 artifacts still validate.

## 1.9.0 - 2026-07-07

- **Configurable verification coverage.** A new `verify_mode` dial controls how many waves get a semantic verifier: `per-agent` (one verifier per dev agent, every wave), `per-wave` (one per wave, every wave -- the default and previous behavior), or `last-wave-only` (verify only the final wave). Set it in a committed `.plan-runner.yml` (`verification.mode`) or per-run with `--verify <mode>`; precedence is flag > file > default.
- **Honest reduced coverage.** Waves left unverified by a lower mode are recorded `SKIPPED` -- a deliberate, transparent absence distinct from `UNVERIFIABLE` (a *requested* verdict that never landed, still a tracked bug). BLOCKED dev agents on a SKIPPED wave still surface a P0, relayed by the orchestrator from the dev's own declared status (no self-verify). The coverage gate leaves SKIPPED alone but still backfills UNVERIFIABLE for an in-scope missing verdict, so a PR still cannot open while a requested verdict is outstanding.
- **Depth-honest surfacing.** The zero-bug summary and cross-cycle convergence hint no longer read as fully verified-clean when waves were skipped; the auto-re-run carries the effective mode forward; and the PR opens as a **draft** with a `[!WARNING]` verification banner whenever any wave was left unverified. The manifest gains an optional `verification` block (`mode` + coverage counters).

## 1.8.0 - 2026-07-02

- **Rogue-commit guard.** A dev agent that disobeys the no-commit rule and commits its own work leaves a clean working tree, which the orchestrator previously misread as "agent produced nothing" -- triggering a wasted retry agent, and mislabeling the wave commit as "no changes". The run skill now records `wave_start_sha` at the start of every wave (when git is available) and, before treating any dev agent as silent-failed or dispatching a retry, checks `git log <wave_start_sha>..HEAD -- <owned_files>`; self-committed work counts as delivered and flows to the wave verifier as usual. The wave-commit step (4e) likewise distinguishes a genuinely empty wave from one self-committed by agents (`skipped_reason = "self-committed by dev agents (rogue)"`, with the real HEAD recorded as `commit_sha`). All checks are gated on `git_available`.
- **Sharper plan-dev git prohibition.** The dev-agent rule now names the forbidden commands (`git add` / `git commit` / `git push`) and explains why a self-commit is harmful, instead of the softer "Do NOT commit".

## 1.7.0 - 2026-07-02
