## Portable role loading and host facilities

Resolve bundled files relative to this `SKILL.md`, not the current working directory. The role directory is `../../agents/`; the schema directory is `../../schemas/`; the script directory is `../../scripts/`; and the sibling PR skill is `../pr/SKILL.md`. Before dispatching an analyzer, developer, test author, verifier, aggregator, or integrator, resolve the corresponding role file to an absolute path and deliver the complete role definition to that subagent **by reference** (`role_delivery = "path"`, the default). The prompt's first line is:

    ROLE DEFINITION: read <absolute role path> in full before anything else and follow it as your instructions for this task. If you cannot read that file, reply with exactly ROLE_FILE_UNREADABLE and stop.

followed by the per-invocation parameters. **Do NOT paste a bundled role file's text into a prompt.** Every character of a prompt is generated by you, token by token, before the subagent can start, and then stays in your context for the rest of the session: pasting a role file into six concurrent dev prompts costs minutes of pure dictation every time, and tens of thousands of context tokens per phase, to hand each subagent text it can read from disk in one tool call. The same rule governs every other bulk input in this pipeline -- the plan (Step 2) and gate output (Step 4c) travel as file paths, never as prompt text. This is the by-reference handoff the relay phase runner (Step 3-bis.2) and the Step 6 re-run already use for this skill file. Exactly two dispatches still carry pasted definition text, each for a stated reason (Step 4a): a project-agent dev dispatch, whose untrusted definition must sit above the contract that overrides it, and an endpoint-bound dispatch, whose model has no tools to read a file with.

**Inline fallback.** If a subagent replies `ROLE_FILE_UNREADABLE` (a sandbox that cannot read outside the workspace), re-dispatch that one agent with the role body pasted in place of the `ROLE DEFINITION` line, set `role_delivery = "inline"`, record `"role_delivery": "inline"` at the top level of the cycle-root `manifest.json` so later phase runners and resumed sessions of this cycle start inline instead of each paying a failed dispatch to rediscover it, and print once: `Role delivery: inline (subagents cannot read <role directory>).` Either way the definition reaches the subagent through its prompt, never through native agent registration: Claude Code may expose those files as namespaced agent types, but never depend on that registration: Codex discovers the skills and does not automatically register `agents/` files. The HTTP dispatch driver (`../../scripts/http-dispatch.js`) and fenced-block parser (`../../scripts/fenced-blocks.js`) resolve the same skill-relative way and are invoked with Node directly -- never via `${CLAUDE_PLUGIN_ROOT}` -- on both backends (ADR-0010).

Use the host's native subagent and progress facilities. Parallelize file-disjoint roles in one batch when supported. Model labels are recommendations; use the closest available model without blocking. Use an available structured-input facility at user gates, or ask in plain chat when none exists. A target repo MAY name a concrete model for any pipeline role via a `models:` block in `.plan-runner.yml`; Step 1d-septies resolves that configuration and governs every dispatch site below, including which roles dispatch over a local HTTP endpoint instead of a host subagent.

Follow this pipeline exactly. Do not skip steps. plan-runner has ONE executor: the dependency-ready task DAG (ADR-0006). A task starts as soon as the tasks it depends on are integrated, without waiting for unrelated active or ready work; there are no waves and no wave barriers. The wave executor and its no-Git fallback were removed in 3.0.0 -- a repository without Git or usable worktrees cannot run (Step 1b-bis), and DAG execution is never approximated on a shared working tree.

## Argument parsing

**Internal phase-runner form (relay only).** If the invocation input begins with `--phase-runner <run-state path> --phase <P>`, this is not a normal run: a relay driver dispatched you (Step 3-bis.2) to run the scheduler for one phase in a fresh context. Capture `run_state_path = <run-state path>` and `phase_runner_id = <P>`, set `is_phase_runner = true`, and do NOT tokenize for a plan path or parse any other flag except `--no-project-agents` -- skip pre-flight and analysis (all state is already on disk) and jump straight to Step 3-bis.0, which loads everything else from the run-state. `--no-project-agents` is the one flag this form accepts, because project-agent dispatch is in-session state that `run-state.json` does not carry: the relay driver re-appends it when the parent run was invoked with it (Step 3-bis.2), and a phase runner that receives it sets `no_project_agents_flag = true` before Step 3-bis.0 rebuilds the inventory. For every other invocation set `is_phase_runner = false` and continue below.

Tokenize the skill invocation input on whitespace. The first non-flag token is the plan path (except for a `--resume` invocation, which carries no plan path -- state comes from the run-state; see the `--resume` flag below). Flags:
- `--verbose` -- if present, the analyzer emits per-task `complexity_signals`. If absent, that field is omitted (default; smaller analyzer output).
- `--no-tdd` -- if present, disable TDD and run the classic (non-TDD) pipeline. Set `tdd_enabled = false`. TDD is ON by default; this flag is the only way to turn it off.
- `--test-cmd "<cmd>"` -- optional explicit test command. May include a `{file}` placeholder for single-file runs (e.g. `pytest {file}`). When provided, it is used verbatim and detection is skipped.
- `--phase-size <N>` -- optional integer overriding `phasing.max_integrations_per_phase` (the number of successful integrations per phase). Overrides `.plan-runner.yml`. Capture its value as `phase_size_flag` (unset if the flag is absent).
- `--phase-mode <relay|stop>` -- optional phase execution mode overriding `phasing.mode`. Overrides `.plan-runner.yml`. Capture its value as `phase_mode_flag` (unset if the flag is absent).
- `--no-phasing` -- if present, disable phasing entirely and run the whole graph in one scheduler session regardless of plan size or yml config. Set `no_phasing_flag = true`.
- `--no-project-agents` -- if present, disable project-agent dispatch for this run: every pipeline role is served by its bundled definition, exactly as before the feature existed. Overrides `.plan-runner.yml` `agents.project`. This is the project-agent kill-switch. Set `no_project_agents_flag = true`.
- `--no-model-config` -- if present, ignore any `models:` block in `.plan-runner.yml` for this run: every role resolves exactly as it did before this feature, and the availability gate is never opened. Overrides `.plan-runner.yml` `models.enabled`. This is the model-policy kill-switch. Set `no_model_config_flag = true`.
- `--base <ref>` -- internal, passed by the Step 6 fix-plan re-run: base this cycle's run-owned branch on `<ref>` (the previous cycle's integration branch) instead of the operator's `HEAD`, so fixes land on top of the work they fix. Capture its value as `base_flag` (unset if absent).
- `--resume [run-state path]` -- resume an interrupted run from its durable task state. With a path argument, resume that specific `run-state.json`. Bare (no path), auto-detect the most recent incomplete run-state under the resolved `docs_base`'s `plan-runner/` tree (plus the legacy `docs/plan-runner/` when `docs_base` differs from `docs`; see R.1). A `--resume` invocation carries NO plan path -- everything is read from the run-state. Set `resume_flag = true`; if the token immediately following `--resume` exists and is not itself a flag, capture it as `resume_path` and consume it (it is the run-state path, never the plan path); otherwise leave `resume_path` unset.

**Removed in 3.0.0 (wave-executor flags).** `--verify <mode>`, `--sync-verify`, and `--execution-mode dag` are accepted and ignored, consuming their value token, with one printed line each: `<flag> is ignored since 3.0.0: every task is independently verified, off the scheduler's critical path, and the task DAG is the only executor.` `--execution-mode wave` -- and `execution.mode: wave` in `.plan-runner.yml` -- cannot be honored; print and STOP:

```
Error: the wave executor was removed in plan-runner 3.0.0. Plans run as a task DAG only.
Remove --execution-mode wave / execution.mode: wave and re-run (Git with usable worktrees is required).
```

Set `verbose = true | false` based on the flag. Capture any `--test-cmd` value as `test_cmd_flag`. Set `tdd_enabled = false` if `--no-tdd` is present, otherwise `tdd_enabled = true` (TDD is auto-enabled by default -- never prompt for it). Capture any `--base` value as `base_flag`. Capture any `--phase-size` value as `phase_size_flag` and any `--phase-mode` value as `phase_mode_flag`. Set `no_phasing_flag = true` if `--no-phasing` is present, otherwise `no_phasing_flag = false`. Set `no_project_agents_flag = true` if `--no-project-agents` is present, otherwise `no_project_agents_flag = false`. Set `no_model_config_flag = true` if `--no-model-config` is present, otherwise `no_model_config_flag = false`. Set `resume_flag = true` if `--resume` is present, otherwise `resume_flag = false`, and capture its optional path token as `resume_path` (see the flag above). Strip all flags (including the ignored ones and any consumed value token) before using the plan path. On a `--resume` invocation there is no remaining plan-path token, and that is expected -- do not treat its absence as the "plan file not found" error.

## Gate discipline

Every test command the orchestrator runs -- the baseline capture (Step 1d-bis), each task's red/green gates and scoped checks (Step 4c), the boundary suite (Step 4h), and the final full-suite verification (Step 4j) -- follows these four rules. They exist because gates, not agents, dominated the wall-clock of real runs: one failing browser suite cost about 55 minutes every time it ran, and one phase runner sat idle for four hours on a gate that had already finished.

1. **File-backed output.** Redirect the command's stdout and stderr to a log file under `$cycle_dir/gates/` (`baseline.log`, `<task_id>-a<n>-<red|green|scope>-<k>.log`, `suite-phase-<P>.log`, `final-suite.log`) and write its exit code to `<log>.exit`: `( <cmd> ) > "<log>" 2>&1; echo $? > "<log>.exit"`. Never stream a gate's output into your own context and never paste it into a prompt. Read the exit code from `<log>.exit`, and pull what you need out of the log with Grep or a bounded `tail`: the test count from the runner's summary line, and the failing test identifiers from its failure lines (`test <id> ... FAILED`, `FAILED <id>`, `--- FAIL: <id>`, or the runner's equivalent), written sorted to `<log>.failing.txt` so a set difference is a shell `comm`, not a judgment. The verifier receives the log's absolute path and reads it itself (Step 4d). Gate logs are retained cycle artifacts.
2. **Time budget.** Every gate command has a budget (resolved in Step 1d-bis): `gates.targeted_timeout_minutes` for a single-file red/green run, `gates.suite_timeout_minutes` for a full-suite run (baseline, boundary suite, final verification) and for a worktree `setup` command. A gate that exhausts its budget is killed, process tree included, and recorded `result: "TIMEOUT"` with `valid_red` / `valid_green` left `null` and `GATE TIMEOUT after <n>m` appended as the log's last line. Enforce the budget mechanically -- wrap the command (`timeout --kill-after=10 <n>m <cmd>`, or the host's equivalent) rather than watching a clock yourself. A timeout is evidence that the gate did not finish -- never a pass, and never a fabricated failure list. The verifier flags it and it flows through the normal fix-plan loop.
3. **Wait in the foreground; never end your turn on a gate.** Run the gate as a foreground command with the host's maximum command timeout. When the budget exceeds what one foreground command may run, launch the gate detached (writing `<log>`, `<log>.exit`, and its process id to `<log>.pid`), then block on it with consecutive foreground waits, each returning when `<log>.exit` exists or the host limit nears, until the marker appears or the budget expires. **Never end your turn, return, or go idle "waiting on" a monitor, watcher, timer, or background-completion notification while a gate is outstanding.** A subagent that ends its turn has returned -- nothing it armed will wake it -- and a phase runner that returns mid-gate stalls the whole run until a human notices.
4. **Did-not-run is its own state.** A suite run that exits non-zero while yielding zero failing test identifiers (a build, compile, or collection failure) did not run. Record it `BUILD_FAILED`, never as an empty failure set: "no failing tests" would read as "no regressions".

## Token accounting

plan-runner tallies the tokens consumed by every subagent it dispatches (analyzer, dev and test-author agents, task verifiers, integrators, aggregator) so `manifest.json` carries a per-agent breakdown and a grand total for the whole cycle. This is the foundation for tallying the full run's token cost.

There is no tool that returns a subagent's token count directly, so capture is **best-effort** from these sources, applied per subagent in strict precedence order:

1. **Harness completion usage (authoritative).** When a subagent completes, read the token usage reported in its completion result (the Task/Agent result's usage summary, e.g. input/output token counts). Record it as `{"input": <n>, "output": <n>, "total": <input + output>, "source": "harness"}`. If only a single combined total is surfaced, record `{"input": null, "output": null, "total": <n>, "source": "harness"}`.
2. **Agent self-report (fallback).** Every pipeline agent bubbles up a `token_usage` field in its return JSON: the most recent usage figure the harness surfaced to it in-band (e.g. a token-budget system warning), or `null` when none appeared. When the completion result carries no usage figure -- common for teammates on the `teams` backend, whose usage may not be visible to the lead -- use the agent's non-null self-report instead: record its fields with `"source": "self_report"` and count the agent as reported. A self-report is a lower bound (the figure predates the agent's final response), but it is a real harness figure, not an estimate.
3. **Endpoint usage (authoritative, endpoint-bound roles only).** A role dispatched over `models.endpoint` (Step 1d-septies) has no harness completion result at all -- the orchestrator called the endpoint itself -- so its usage comes from the response record's `usage` object instead: record `{"input": <prompt_tokens>, "output": <completion_tokens>, "total": <total_tokens>, "source": "http_usage"}` and count that role as reported. When the response reports no usage object, record `tokens: null` exactly as the no-figure case below -- an HTTP response is never a reason to estimate a value either.

If no source yields a figure, record `tokens: null` (no `source`) and count the agent as unreported. **Never fabricate a token count** -- a `null` with an honest coverage number is the correct outcome when the figure is unavailable, and an agent's `token_usage: null` must never be "rescued" with a guess.

**The tally is durable, not in-memory.** Append each entry to `token_usage.by_agent` in the cycle-root `manifest.json` at the moment that subagent's usage is captured (or found missing), so a crashed, stopped, or recovered scheduler session never takes its agents' entries with it, and every phase runner writes to the same one tally. Finalization (Step 5) recomputes the roll-up fields from that array:

```json
{
  "by_agent": [
    {"agent": "analyzer", "phase": "analyze", "input": <n|null>, "output": <n|null>, "total": <n|null>, "source": "harness | self_report | http_usage -- omit when tokens are null"}
  ],
  "total_tokens": <sum of every non-null per-agent total>,
  "agents_reported": <count of subagents that surfaced a usage figure>,
  "agents_total": <count of subagents dispatched this cycle>,
  "complete": <agents_reported == agents_total>
}
```

Append one `by_agent` entry per dispatched subagent, labeled by task and attempt: the analyzer (`{"agent": "analyzer", "phase": "analyze", ...}`); every dev or test-author dispatch (`{"agent": "<task_id>-a<attempt>", "phase": "task", ...}`); every task verifier (`{"agent": "<task_id>-a<attempt>-verifier", "phase": "verify", ...}`); every integrator dispatch (`{"agent": "<task_id>-integrator", "phase": "integrate", ...}`); and the aggregator (`{"agent": "aggregator", "phase": "aggregate", ...}`). An agent that was dispatched but whose session was lost before its usage could be read still gets its entry, with `null` tokens: work that ran always counts toward `agents_total`.

### End-of-run Run Report

It is rendered from the finalized `token_usage` tally and the `dag.tasks` outcomes in the cycle-root `manifest.json`, plus the phase-timing tally, so on a phased run it reflects the entire multi-phase cycle rather than just the terminal scheduler session. It prints once, as the last output before STOP, on every terminal path: the clean run, and the bugs-found run after the user declines the re-run. It does NOT print on the bugs-found re-run *handoff* path (user picks `Y`) -- that intermediate cycle prints only the compact decision block (Step 6) and hands off; its full tally still lands in `manifest.json`.

Bugs-found run -- same skeleton, three deltas: the title reads `plan-runner cycle <n> -- <N> bugs found (P0:<n> P1:<n> P2:<n> P3:<n>)`; the `Bugs` stat shows `<N>`; and the Artifacts block gains `Bug report` and `Fix plan` rows. Rendering rules:

- **Title.** `COMPLETE (clean, no bugs found)` when `total_bugs == 0` and no task is blocked; otherwise `<total_bugs> bugs found (P0:<n> P1:<n> P2:<n> P3:<n>)`.
- **Stat header** is a two-column grid of label/value pairs. `Tasks` = `<T> (<integrated> integrated)`; `Dev agents` = total dev and test-author dispatches, repairs and re-executions included; `Verifiers` = `<verdicts captured>/<verdicts requested> tasks`; `Repairs` = count of repair and re-execution attempts; `Duration` = total elapsed, `Xm Ys`; `Tokens` = `token_usage.total_tokens` with thousands separators; `Coverage` = `<agents_reported>/<agents_total> agents`; `Bugs` = `total_bugs`.
- **Honesty lines** (each prefixed `! `) print directly under the stat header, above the tables, and only when they apply:
  - partial token coverage -- printed only when `token_usage.complete` is false; the totals are a lower bound. Wrap at the 60-column width with a two-space hanging indent.
  - blocked tasks -- printed only when at least one task ended `blocked`.
  - unverifiable final suite -- `! The final full-suite verification did not complete (<BUILD_FAILED | TIMEOUT>); no PR was opened.`
- **Dispatch provenance.** `Dev agents` counts every dev dispatch; when at least one was served by a project agent, append ` (<n> project)` to that value and print one `Served by:` line under the honesty lines, tallying each serving definition from the manifest `agent_source` values: `Served by: plan-dev (bundled) <n>, <name> (project) <n>, ...`. When every dispatch was `bundled` -- the feature disabled, or an empty inventory -- omit both the suffix and the `Served by:` line.
- **Tokens by phase** table: group `by_agent` entries by `phase` (`analyze` -> Analyze, `task` -> Dev, `verify` -> Verify, `integrate` -> Integrate, `aggregate` -> Aggregate); omit a phase row entirely when no subagent was dispatched in that phase (e.g. Integrate when every integration took the mechanical fast path, Aggregate on a zero-bug run). `Agents` = subagents dispatched in the phase; `Reported` = how many surfaced a usage figure. Input / Output / Total are sums of the **non-null** values only, with thousands separators; print `n/a` for a cell where nothing in that phase reported a figure. Never fabricate a number. The `Total` row's Total cell equals `token_usage.total_tokens`. `Top consumers` lists up to 3 agents with the largest non-null `total`, formatted `<agent> (<total>)`; omit the line when no agent reported. The coverage figure is not repeated here -- it lives once, in the stat header.
- **Timing by phase** table lists each phase's elapsed time as `Xm Ys`: Pre-flight, Analyze plan, Task execution (annotated `(<T> tasks, critical path <n>)`, summed across scheduler sessions on a phased run), Final suite, Aggregation (omit the row on a zero-bug run, where no aggregator ran), Sync code atlas (mark skipped when code-atlas is not present), Open PR (mark skipped when the PR step did not run), and a `Total`. `User confirm` is excluded from the total.
- **Artifacts** always lists `Manifest`; it adds `Bug report` and `Fix plan` rows only when `total_bugs > 0`.

### Intermediate phase summary (phased runs)

At every **non-terminal** phase boundary a phased run prints a compact phase summary -- **never the full Run Report**, which is a terminal-only, once-per-run artifact. The relay driver prints it after each phase-runner returns (Step 3-bis.2); a stop-mode session prints it before ending at the boundary (Step 3-bis.3); the wall-time guardrail reuses the stop form (Step 3-bis.4). It is a small fixed block covering the run so far and nothing more:

```
Phase <P>/<phase_count> complete -- <integrated>/<T> tasks integrated (<blocked> blocked)
  Bugs so far    <cumulative bug count>
  Tokens so far  <sum of non-null totals> (<agents_reported>/<agents_total> agents)
  Boundary suite <passed | <n> regressions | did not run (<reason>) | skipped (suite cannot finish in budget)>
  Next           <phase <P+1>: relay dispatch | stop + resume | resume command>
```

- **Bugs so far** and **Tokens so far** are cumulative, read from the cycle-root `manifest.json` and the `bugs/` directory already on disk, so the operator sees the run's running total while the driver holds no task-level context. Tokens sum **non-null values only**; when coverage is partial (`agents_reported < agents_total`), append ` -- lower bound` to the Tokens line, mirroring the Run Report's honesty rule. Never fabricate a token count for an agent that stayed `null`.
- **Next** names what follows this boundary: relaying into phase `<P+1>`, or stopping with the copy-pasteable resume invocation (stop mode, guardrail, or teams backend). This block is compact by contract -- it MUST NOT expand into the token/timing tables, the status header, or the artifacts list of the full Run Report. The full Run Report prints exactly once, only at the terminal end.

## Step 1: PRE-FLIGHT

If `is_phase_runner` is true, this invocation is a relay phase-runner: skip Steps 1, 2, and 3 entirely (all state is already on disk) and execute Step 3-bis.0 directly. A phase runner never resolves `docs_base` itself -- `cycle_dir` is derived from `run_state_path`'s parent directory (Step 3-bis.0), which already lives under whatever base the original run resolved.

### 1a-minus. Resolve output base

Every other invocation -- a fresh run and an explicit `--resume` alike -- resolves `docs_base` here, before any resume discovery or plan validation runs, because both the Step 1a-0 auto-detect scan and the bare-`--resume` scan (R.1) glob under `docs_base`. Resolve using only directory listing / Glob and reading `CLAUDE.md` / `AGENTS.md` -- no YAML parser, no shell-specific tooling -- so the result is deterministic for a given repository state:

1. **Explicit statement.** Check, in order, the repo-root `CLAUDE.md`, the repo-root `AGENTS.md`, and any repository instructions already loaded into context this session (e.g. a project `CLAUDE.md` the host injected at session start). Look for a sentence that **explicitly** names a documentation directory (e.g. "docs live in `documentation/`", "project docs are under `doc/`"). A generic or vague mention of "docs" without a named directory does not count -- fall through to the next rule. If an explicit statement is found, set `docs_base` to the named directory (strip any trailing slash) and `docs_base_source` to whichever file supplied it (`CLAUDE.md` takes precedence over `AGENTS.md` when both name a directory; in-context repository instructions count as their source file, typically `CLAUDE.md`).
2. **Top-level scan.** Otherwise, list the repo-root top-level entries (Glob or a directory listing) and check, in this fixed order, for a directory literally named `docs`, `doc`, `documentation`, `.docs`. Set `docs_base` to the first one that exists and `docs_base_source = "top-level scan"`. If two or more of these directories exist simultaneously, still pick only the first match in this order -- never create or use a second base. Decide which candidates exist from the listing's *output*, never from its exit status: a listing naming all four candidates exits non-zero whenever any one of them is missing, which is the normal case, and that exit status is not evidence about the other candidates or about any other file.
3. **Default.** Otherwise (no explicit statement, no known-name top-level directory), set `docs_base = "docs"` and `docs_base_source = "default"` -- byte-for-byte today's behavior, including creating `docs/` as Step 1b already does.

Store `docs_base` and `docs_base_source` for Step 1b (`cycle_root`), the resume-discovery globs (1a-0 and R.1), and Step 1e (manifest).

Print the resolved output base and its source now, unconditionally, as soon as `docs_base` resolves -- before the `resume_flag` check below, so both a fresh run and an explicit `--resume` invocation see it:

    Output location: <docs_base>/plan-runner/ (from <CLAUDE.md | AGENTS.md | top-level scan | default>).

If `resume_flag` is true, this is an explicit resume invocation: run Step 1a-minus-bis below (every invocation loads the configuration), then skip the rest of this fresh pre-flight and Steps 2 / 3 and execute the **Resume and crash recovery** section directly (entry: explicit `--resume`), which consumes `docs_base` resolved above for its bare-scan glob (R.1). A resume still requires Git and usable worktrees: run Step 1b-bis's checks first.

Record the pipeline start time: `t_start = $(date +%s)`.

### 1a-minus-bis. Load `.plan-runner.yml`

Every invocation that reaches Step 1 -- a fresh run and an explicit `--resume` alike -- loads the repo-root `.plan-runner.yml` here, once, before any setting resolves. Every later step consumes what this step loaded and none of them re-reads the file: the `worktree` block (1c-ter), the `gates` block (1d-bis), the `phasing` block (1d-quinquies), `agents.project` (1d-sexies), and the `models` block (1d-septies). A leftover `execution.mode: wave` is the one key that stops the run (see **Argument parsing**); `verification.mode` and `verification.pipelined` are ignored since 3.0.0.

Read `.plan-runner.yml` at the repo root with the Read tool, as a standalone operation. On success set `config_text` to the file's contents and `config_present = true`. Otherwise set `config_present = false` and leave `config_text` empty.

**Absence is established only by the Read tool reporting that `.plan-runner.yml` does not exist.** Never infer absence from anything else: not from the exit status of a directory listing, not from a glob that matched nothing, and above all never from a shell command that chains the read behind another command. `ls docs doc documentation .docs && cat .plan-runner.yml` is the exact shape to avoid -- the candidate-directory listing from 1a-minus exits non-zero whenever any candidate directory is missing, which is the normal case, so the chained read never runs and the file is misread as absent. That misreading is silent and total: a single false absence reverts the worktree bootstrap, gate budgets, phasing, project-agent dispatch, and model policy to their defaults at once, with nothing but the `(from default)` parentheticals to show for it. One read, on its own, no chaining.

Treat any failure that is not a not-found result -- a permissions error, a decode error -- as unreadable rather than as evidence about the repository: set `config_present = false` and say so on the console.

Print the result now, unconditionally, so a misread is visible rather than silent:

    Config: .plan-runner.yml loaded.

or, when the Read tool reports the file does not exist:

    Config: no .plan-runner.yml at repo root -- using defaults.

or, when it exists but could not be read:

    Config: .plan-runner.yml unreadable (<reason>) -- using defaults.

Store `config_present` and `config_text` for 1c-ter, 1d-bis, 1d-quinquies, 1d-sexies, 1d-septies, and the resume re-resolution in **Resume and crash recovery**.

### 1a-0. Auto-detect resumable runs

### 1b-bis. Require Git and usable worktrees

Task-DAG execution is the only executor, and it needs Git: every task runs in its own disposable worktree and only verified commits reach a run-owned branch. Check, in order:

1. `git rev-parse --is-inside-work-tree 2>/dev/null` succeeds and prints `true`.
2. `git rev-parse --verify HEAD` succeeds (the repository has at least one commit to base the run on).
3. Worktrees are usable. Probe without changing the operator's checkout: create a disposable detached worktree in a host temporary directory at `HEAD`, remove it with `git worktree remove --force`, and `git worktree prune`.

If any check fails, print the reason and STOP. **Never approximate DAG execution on a shared working tree**, and never attempt task-worktree dispatch after a failed probe:

```
plan-runner needs a Git repository with usable worktrees: every task runs in its own
disposable worktree, and only verified commits reach a run-owned branch.
  reason: <git is not installed | not a git repository | the repository has no commits | worktree probe failed: ...>

To prepare this directory:
  git init
  (add a .gitignore for build output and dependencies first)
  git add -A && git commit -m "baseline"
Then re-run. Nothing was changed.
```

Set `git_available = true` for the manifest. (Before 3.0.0 a repository without Git fell back to a wave executor; that executor no longer exists.)

### 1c. Clean base and run-owned integration branch

Validate the checkout before creating any run branch. When `base_flag` is set (a fix-plan re-run), `base_ref = git rev-parse <base_flag>`: require it to resolve, print `Base: <base_flag> (previous cycle's integrated work).`, and skip the dirty-checkout prompt below -- nothing is read from the operator's working tree. Otherwise a clean checkout captures `base_ref = git rev-parse HEAD`. A dirty checkout is never silently accepted; run `git status --porcelain` and, if its output is non-empty, ask once:

```
DAG execution requires an unambiguous base checkout. The working tree has changes:
<git status --porcelain>

[s] stash tracked and untracked changes, then create the run branch
[a] abort DAG execution

(s/a)
```

Only `s` runs `git stash -u`; any other response stops. The stash is the operator's to restore: print `Stashed your changes -- restore them with "git stash pop" whenever you like; this run never touches your checkout again.` After that explicit decision, capture `base_ref`. Do not create a branch from a dirty tree and do not silently stash or discard operator work.

Create a run-owned integration branch named `plan-runner/<YYYY-MM-DD>/cycle-<N>` at `base_ref`, and create a dedicated integration worktree for it outside the operator checkout, in a host temp location. The operator's active branch is never checked out, committed to, reset, or merged by plan-runner. If the branch already exists, stop unless this is a validated resume whose state records the same owned branch and base (R.3). Create an initially empty append-only `events.jsonl` in the cycle directory, choose a `run_id` for it, and record `base_captured` and `integration_branch_created` events before any task dispatch. The integration worktree's path is never persisted: any later session finds it with `git worktree list --porcelain` (the entry whose branch is `refs/heads/<integration branch>`).

**A STOP before the first dispatch cleans up what this step created.** If the run stops anywhere between here and Step 4 (a settings validation error, a missing test command, a configuration error, a malformed task graph, zero tasks), remove the integration worktree and delete the run-owned branch (`git worktree remove --force`, then `git branch -D`) before stopping: nothing was integrated, and a leftover branch would make the next run's branch-exists check stop it.

### 1c-ter. Worktree bootstrap

Resolve the gate budgets first -- run Step 1d-bis's **Resolve gate settings** paragraph now, ahead of its position in this file -- because a worktree `setup` command runs under the suite budget.

A fresh worktree contains only what Git tracks. Installed dependencies and build caches (`node_modules`, `.venv`, `target`) are absent from it, so without help every task's gates would reinstall or cold-build the project -- or simply fail to start. `.plan-runner.yml` MAY carry a `worktree` block; extract each key directly from `config_text` (Step 1a-minus-bis):

```yaml
worktree:
  setup: ""       # command run once in every new worktree before any gate, e.g. "npm ci --prefer-offline"
  share: auto     # auto (default) | none | a list of repo-relative untracked directories
```

- `share` names untracked directories to **link** from the operator checkout into every new worktree at the same relative path (a symlink, or a directory junction on Windows) instead of rebuilding them per task. `auto` resolves to whichever of `node_modules`, `.venv`, `venv`, and `vendor` exist at the repository root and are untracked. List a build-output directory (`target`, `.next`, `dist`) explicitly, and only when concurrent builds sharing it are safe for that toolchain (cargo, for one, serializes on a lock and keeps the cache warm).
- `setup` runs after linking, once per new worktree, under the suite budget of **Gate discipline**; a failing setup is recorded in that worktree's first gate log and surfaces as that gate's `BUILD_FAILED`.
- A link is never task output. Stage task work with every shared name excluded (`git add -A -- . ':(exclude)<name>'` for each), so a link can never reach a task commit or trip the ownership diff.
- **Unlink before you remove.** Before removing ANY worktree, delete each link itself (`rmdir` on a junction, `rm` on a symlink) -- never a recursive delete that could follow the link into the operator's real `node_modules` or build cache. Only then run `git worktree remove --force`.

Apply the bootstrap to the integration worktree now, and to every task worktree when it is created (Step 4a). Print:

    Worktree bootstrap: setup <"<cmd>" | none>, sharing <comma-joined directories | nothing>.

### 1c-bis. Pick analyzer model (structure heuristic)

Before dispatching the analyzer, compute a cheap structure score on the plan contents:

- `task_boundary_count` = number of lines matching `^## ` OR `^### Task` OR `^Task \d+:` (case-sensitive).
- `path_token_count` = number of tokens matching `(?:[\w.-]+/)+[\w.-]+\.[A-Za-z0-9]{1,5}` (path segments with a file extension).

Use available shell tools such as `awk` / `grep -c` to count -- the plan never enters your own context (Step 1a).

Decision:
- If `task_boundary_count >= 2` AND `path_token_count >= 2` AND `path_token_count >= task_boundary_count`: set `analyzer_model = "haiku"`. The plan is well-structured; DAG inference is mostly mechanical.
- Otherwise: set `analyzer_model = "sonnet"`.

Print one of:
```
Plan structure detected (N task markers, M explicit paths) -- using haiku for analyzer.
Plan is free-form -- using sonnet for analyzer.
```

### 1d-bis. Resolve gate settings, test command + green baseline

**Resolve gate settings (always, even when TDD is off -- a worktree `setup` command consumes the suite budget).** `.plan-runner.yml` MAY carry a `gates` block; extract each key directly from `config_text` (Step 1a-minus-bis), and fall through to the default on a missing file or key:

```yaml
gates:
  targeted_timeout_minutes: 10   # budget for one single-file red/green run
  suite_timeout_minutes: 30      # budget for one full-suite run (baseline, boundary suite, final verification)
```

Both budgets must be positive integers; print an error and STOP on anything else. (The pre-3.0.0 `gates.suite_cadence` and `gates.invalid_red` keys belonged to the wave executor and are ignored.) Print:

    Gates: targeted <n>m, suite <n>m (from <.plan-runner.yml | default>).

If `tdd_enabled` is false, skip the rest of this step (no test command, no baseline).

**Resolve the command** in priority order:
1. If `test_cmd_flag` is set, use it. If it contains `{file}`, that is the single-file form; derive the full form by removing the `{file}` token AND any now-dangling argument separator or trailing whitespace (e.g. `npm test -- {file}` -> `npm test`, `pytest {file}` -> `pytest`). Otherwise treat it as the full form and derive a single-file form if the runner supports it.
2. Otherwise detect from repo markers (use Glob/Read, do not guess blindly):
   - `package.json` with `scripts.test` -> full: `npm test`, single-file: `npm test -- {file}`
   - `pytest.ini` / `pyproject.toml` / `setup.cfg` with pytest -> full: `pytest`, single-file: `pytest {file}`
   - `go.mod` -> full: `go test ./...`, single-file: `go test ./{dir}`
   - `Cargo.toml` -> full: `cargo test`, single-file: `cargo test {mod}`
   - `*.csproj` / `*.sln` -> full: `dotnet test`, single-file: `dotnet test --filter {file}`
3. If detection is ambiguous or finds nothing, prompt the user once:

```
No test command detected. Enter the test command (use {file} for single-file runs),
or press Enter to STOP (re-run with --no-tdd for the classic pipeline):
```

   If the user supplies a command, use it. **If the user enters nothing, STOP** with:

```
No test command available -- cannot run TDD gates.
Re-run with --no-tdd to use the classic pipeline.
```

   Do NOT silently downgrade to classic.

**Capture the green baseline.** Run the full test command in the bootstrapped integration worktree (Step 1c / 1c-ter) -- the clean base every task starts from, never the operator's possibly-stashed checkout -- under **Gate discipline** (log: `$cycle_dir/gates/baseline.log`, budget: the suite budget) and record its wall-clock as `baseline_suite_seconds`. `baseline_failing` is the extracted failing-identifier set (`baseline.log.failing.txt`; empty if the suite is green). Record `baseline_state`:

- `green` -- ran, nothing failing.
- `red` -- ran, some tests failing. Print a warning that the baseline is not clean and that the listed failures will be subtracted when attributing new failures.
- `build_failed` or `timeout` -- the suite did not run (Gate discipline rules 4 and 2). `baseline_failing` is empty because nothing ran, not because the suite is green: print a warning saying so, and add the line `BASELINE DID NOT RUN` to every later suite result (Steps 4h and 4j) so failures are never presented as proven regressions.

**The full suite runs rarely, by design.** Each task is gated by its own targeted runs and scoped checks (Step 4c); the FULL suite runs only here, at each phase boundary (Step 4h), and once at the end (Step 4j). When `baseline_state` is `timeout` the boundary suites are skipped -- a suite that cannot finish inside its budget would burn that budget at every boundary and still prove nothing -- and the warning names the two ways out (a faster `--test-cmd`, or a larger `gates.suite_timeout_minutes`); the final verification is still attempted once.

Store the resolved command (both forms), `baseline_failing`, `baseline_state`, `baseline_suite_seconds`, and the resolved gate settings for the manifest `tdd` block (Step 1e) -- a relay phase runner (Step 3-bis.0) and a resumed session (R.5) read them back from there instead of re-detecting the command or re-running the baseline.

### 1d-quinquies. Resolve phasing config

A large plan run in one long-lived scheduler session grows that session's context and host-process memory without bound, which crashes constrained machines. Phasing bounds it: the scheduler checkpoints after a configured count of successful integrations, and each phase runs in a fresh context. Phasing checkpoints after successful integrations, not after waves -- there are no waves. Resolve the configuration now; whether it activates is decided in Step 3 once the task count is known.

`.plan-runner.yml` MAY carry a `phasing` block:

```yaml
phasing:
  enabled: true                    # default true
  max_integrations_per_phase: 12   # default 12
  mode: auto                       # auto (default) | relay | stop
  auto_stop_phases: 3              # auto mode: relay up to this many phases, stop above
  relay_max_minutes: 90            # relay guardrail: force stop at the next boundary past this
```

Resolve each setting in precedence order **flag > yml > default**. Extract each key directly from `config_text` (Step 1a-minus-bis) -- do NOT depend on a YAML parser being installed. A missing file, a missing key, or an unreadable file falls through to the default.

- `phasing_enabled`: `false` if `no_phasing_flag` is true (the kill-switch wins over everything); otherwise the yml `phasing.enabled` value; otherwise `true`.
- `max_integrations_per_phase`: `phase_size_flag` if set; otherwise the yml `phasing.max_integrations_per_phase` value; otherwise `12`. Must be an integer >= 1; if the resolved value is not a positive integer, print an error and STOP. It is the only phase boundary. (A pre-3.0.0 `phasing.max_waves_per_phase` key is ignored; print one line saying so if it is present.)
- `phase_mode`: `phase_mode_flag` if set; otherwise the yml `phasing.mode` value; otherwise `auto`. Validate against {`relay`, `stop`, `auto`}; if it is anything else, print an error and STOP.
- `auto_stop_phases`: the yml `phasing.auto_stop_phases` value; otherwise `3`.
- `relay_max_minutes`: the yml `phasing.relay_max_minutes` value; otherwise `90`.

Print the resolved config and its trigger threshold:

    Phasing: <enabled|disabled>. Threshold: ><max_integrations_per_phase> tasks (max_integrations_per_phase=<max_integrations_per_phase>), mode=<phase_mode>.

When `phasing_enabled` is false, print instead:

    Phasing disabled (--no-phasing or phasing.enabled: false) -- running the whole graph in one scheduler session.

Store `phasing_enabled`, `max_integrations_per_phase`, `phase_mode`, `auto_stop_phases`, and `relay_max_minutes` for Step 3 and the run-state checkpoint.

### 1d-sexies. Resolve project-agent dispatch and build the agent inventory

A target repo may ship its own specialized agents (a frontend expert, a Rust expert) that implement a dev task better than the generic bundled `plan-dev`. Resolve whether to use them, then build the inventory Step 4a selects from.

**Resolve the setting** in precedence order **flag > yml > default**, the same precedence pattern as the phasing settings:

1. `project_agents_enabled = false` if `no_project_agents_flag` is true (the `--no-project-agents` kill-switch wins over everything).
2. Otherwise, if `config_present` (Step 1a-minus-bis), use the `agents.project` value from `config_text`. Extract that single key directly -- do NOT depend on a YAML parser being installed. A missing file, a missing `agents.project` key, or an unreadable file falls through to the next step.
3. Otherwise default to `true` -- the feature is on by default.

Print the resolved setting and its source:

    Project-agent dispatch: <enabled|disabled> (from <--no-project-agents flag | .plan-runner.yml | default>).

**When `project_agents_enabled` is false, skip discovery entirely:** set `agent_inventory = []` and `routing_directives = []`, scan nothing, and print no further lines. Step 4a then uses only bundled role definitions and its dispatch is byte-identical to pre-feature behavior. Proceed to Step 1e.

**Otherwise build the inventory** (in-session state; see the note at the end of this step):

1. **Collect candidate agent files** from these locations, in this order, using Glob:
   - `.claude/agents/*.md`
   - `.codex/agents/*.md`, when that directory is present
   - any additional agent-file location **explicitly named** by the target repo's `AGENTS.md` or `CLAUDE.md` (e.g. "our agents live in `tools/agents/`"), globbed the same way. A vague mention of "agents" that names no directory does not count.

   A missing directory contributes no entries and is not an error. Deduplicate by resolved path.

2. **Parse each file's frontmatter** and record one inventory entry: `{name, description, tools, model, path}` plus the file's markdown body (kept in session for prompt assembly in Step 4a). `name` falls back to the file's basename without its extension when the frontmatter omits it. **An absent `tools` field means the agent inherits all tools** -- record `tools: null` and treat it as write-capable for the Step 4a tool guard; an explicit `tools` list is recorded verbatim and never widened.

3. **Malformed files are skipped, never fatal.** If a candidate file is unreadable, has no frontmatter, or its frontmatter cannot be parsed, exclude it from the inventory and log one line, then continue with the remaining files:

       Agent inventory: skipped <path> (<unreadable | no frontmatter | unparseable frontmatter: ...>).

   Discovery failures never fail the pipeline.

4. **Collect routing directives** from the repo-root `AGENTS.md` and `CLAUDE.md`: sentences that **explicitly** route work to a named agent, of the form "use agent X for Y work". Record each as `{agent_name, applies_to}`. Only explicit directives count -- a doc that merely mentions an agent's existence, or names work with no agent, produces no directive. A directive naming an agent that is not in the inventory (unreadable, skipped, or absent) is dropped with a logged reason.

5. **Print the inventory summary**, once:

       Agent inventory: <n> project agents discovered (<comma-joined names>), <m> routing directives.

   **An empty inventory with no routing directives prints nothing at all** and yields exactly today's behavior -- a repo with no agent directories and no directives must see no warnings.

The inventory and directives are **in-session state only**: no cycle artifact is written, no schema carries them, and `run-state.json` does not persist them. A resumed session (Resume step R.3) and a relay phase runner (Step 3-bis.0) each rebuild them by re-running this step, so a mid-run edit to an agent file may be picked up on the rebuild. The inventory feeds dev-agent selection in Step 4a and nothing else: the analyzer, test-author, verifier, and aggregator dispatches always use their bundled definitions regardless of what it contains.

(The output base and its source were already printed in Step 1a-minus, immediately after `docs_base` resolved and unconditionally of everything that follows it -- including the clean-tree prompt, missing test command, and gate-settings validation checks that can each STOP the pipeline before this step is reached. Nothing further to print here.)

### 1d-septies. Resolve model policy

A target repo may declare a `models:` block in `.plan-runner.yml` naming the model for any pipeline role, instead of relying solely on this pipeline's built-in defaults (bundled agent `model:` frontmatter, the Step 1c-bis structure heuristic, and the analyzer's per-task `recommended_model`). Tier words (`haiku`, `sonnet`, `opus`) become an abstract vocabulary rather than model names -- this step is what binds them to a concrete identifier. It governs every dispatch site downstream: analyzer (Step 2), dev and test-author (Step 4a), verifier (Step 4d), integrator (Step 4f), and aggregator (Step 5).

The same block also decides *how* a role is dispatched, not only which model serves it: `models.endpoint.roles` names the roles this run dispatches by issuing an OpenAI-compatible chat-completions request to `models.endpoint.base_url` itself (Step 4a), instead of handing a label to a host subagent (ADR-0009). Of the six roles above, only `dev` and `test-author` are eligible -- neither is code-writing work that also needs repository or tool access, unlike the other four (see the eligibility check below).

**Resolve `models_enabled`** in precedence order **flag > yml > default**, the same pattern as the phasing settings:

1. `models_enabled = false` if `no_model_config_flag` is true (the `--no-model-config` kill-switch wins over everything).
2. Otherwise, if `config_present` (Step 1a-minus-bis), use the `models.enabled` value from `config_text`. Extract that single key directly -- do NOT depend on a YAML parser being installed. A missing file, a missing `models.enabled` key, or an unreadable file falls through to the next step.
3. Otherwise default to `true`.

Print the resolved setting and its source:

    Model config: <enabled|disabled> (from <--no-model-config flag | .plan-runner.yml | default>).

**When `models_enabled` is false, this behaves exactly as `--no-model-config`:** skip the rest of this step entirely. Every role resolves exactly as it did before this feature -- bundled `model:` frontmatter, the Step 1c-bis heuristic, `recommended_model`, and the existing "prefer sonnet when available" defaults -- and the availability gate below is never opened. Proceed to Step 1e.

**Otherwise, extract the `models:` block** from `config_text`. Extract each key directly, never via a YAML parser:
- `models.tiers.haiku`, `models.tiers.sonnet`, `models.tiers.opus` -- concrete identifiers for each tier word.
- A per-role key for each of `analyzer`, `dev`, `test-author`, `verifier`, `aggregator`, `integrator`.
- `models.endpoint.base_url` and `models.endpoint.api_key_env`.
- `models.endpoint.roles` -- the list of roles this run dispatches over that endpoint instead of a host subagent (eligibility validated below). Absent or empty means no role is endpoint-bound and every role resolves and dispatches exactly as it did before this feature.
- `models.endpoint.request` -- an optional passthrough object (`timeout_seconds`, `max_tokens`, `body`) that Step 4a's HTTP endpoint dispatch merges over the HTTP dispatch driver's own defaults (a timeout below the ~300s gateway limit, and `chat_template_kwargs: {enable_thinking: false}`) key by key, so a passthrough key overrides its corresponding default without discarding the rest.

`.plan-runner.yml` may be absent, unreadable, or missing a requested key -- any of those falls through to the next precedence level without raising: an absent per-role key falls through to the tier map, and an absent tier entry falls through to the built-in default.

**Build the resolved model map.** For every role, resolve in this precedence:
1. A serving project agent's `model:` frontmatter (dev dispatch only -- unchanged head of the chain from Step 4a; project agents never serve any other role).
2. The `models:` per-role key for that role, if set.
3. The `models.tiers` entry for the tier the role or task calls for (the Step 1c-bis result for the analyzer; the task's `recommended_model` for dev and test-author; `sonnet` for verifier, aggregator, and integrator), if the tiers map declares that tier.
4. The built-in default, unchanged from pre-feature behavior (frontmatter, the Step 1c-bis heuristic, `recommended_model`, or `sonnet`).

A configured value that is not one of the three tier words is a raw model identifier and is passed to the host unmodified -- never validated against a model registry; a typo surfaces at the availability gate below, not here.

**Endpoint preflight**, only when `models.endpoint.base_url` is set:
- If `models.endpoint.api_key_env` names an environment variable, check it directly -- do NOT print or persist its value, only its name. Absent or empty -> the endpoint is unavailable and takes the gate path below.
- Issue at most one health-check request to `base_url` for the whole run, with a 5-second timeout. A failed or timed-out check records the endpoint's health as `"unreachable"` and continues without raising -- it never blocks the pipeline.
- Compare `base_url` against the exported `ANTHROPIC_BASE_URL` environment variable. If they differ, print a warning naming both values and do NOT modify the process environment -- plan-runner never sets `ANTHROPIC_BASE_URL` on the operator's behalf.
- This preflight checks only endpoint reachability, `api_key_env` presence, and config well-formedness. It does NOT attempt to enumerate the host's available models -- that is not locally checkable; an unservable model *name* is caught by the analyzer probe below instead.

**Endpoint role eligibility**, only when `models.endpoint.roles` is non-empty: `analyzer`, `aggregator`, and `verifier` are never eligible. If any of them appears in `models.endpoint.roles`, this is a configuration error, not an honored setting -- print and STOP before dispatching anything:

    Configuration error: models.endpoint.roles names "<role>", which cannot be served over
    an endpoint. Only dev and test-author are eligible; analyzer, aggregator, and verifier
    require repository or tool access an HTTP completion cannot supply.

`integrator` is ineligible for the same reason (it reads evidence files and decides a conflict) and takes the same STOP.

**curl probe**, only when `models.endpoint.roles` is non-empty (and role eligibility above passed): probe that `curl` is executable (an available shell's `curl --version` or equivalent) and record the result. A missing or non-executable `curl` is reported as a named preflight failure, never silently retried later:

    Endpoint preflight: curl is not executable -- endpoint-bound roles cannot dispatch.

A missing `curl` is NOT routed through the availability gate below: an endpoint-bound role with no usable `curl` fails loudly at preflight and is NEVER substituted with a host-dispatched or hosted model, on this or any later failure path (the non-degradable exception below applies here too, and takes precedence over the ordinary gate for this specific cause).

**Print the endpoint role map**, only when `models.endpoint.roles` is non-empty and the two checks above passed: one line per pipeline role, naming its dispatch mechanism, so a run's actual dispatch never silently differs from its configuration --

    Endpoint role map:
      analyzer:    host subagent
      dev:         endpoint (<base_url>)
      test-author: endpoint (<base_url>)
      verifier:    host subagent
      aggregator:  host subagent
      integrator:  host subagent

A role not listed in `models.endpoint.roles` always prints `host subagent`, regardless of whether an endpoint is configured at all.

**Availability gate.** If preflight finds one or more configured entries that cannot be served (endpoint unreachable, `api_key_env` absent/empty, or a malformed config value), ask the operator once, in a single structured question covering every unavailable entry, before any dev agent is dispatched. Use an available structured-input facility, or ask in plain chat when none exists:

    The following configured models cannot be served:
    - <role or tier>: "<configured value>" (<reason>)

    Substitute the closest available model chosen by task complexity for these roles instead? (Y/n)

Cache the answer for the remainder of the run. **If the availability gate has already been answered earlier in the same run, do NOT ask the operator about model availability again for the remainder of that run.**

- **Granted:** substitute the closest available model for the affected roles, chosen by task complexity, record the substitution, and record the answer as `consent: "granted"`.
- **Declined:** do NOT substitute by task complexity. Resolve the affected roles using the pre-feature built-in defaults, record the answer as `consent: "declined"`, and continue the run -- declining never aborts.
- **No structured-input facility available, or the gate goes unanswered:** dispatch the closest available model, print the substitution, and record it. Never abort the run. Record the answer as `consent: "auto"` -- the value that distinguishes an unattended degrade from an operator who was actually asked.

The recorded `consent` vocabulary is exactly `granted`, `declined`, and `auto`, matching the enum in `run-state.schema.json`. When the availability gate is never opened at all -- the ordinary case, where every configured model can be served -- there is no operator answer, so `consent` is OMITTED from `model_policy` rather than being given a placeholder value.

**Exception -- endpoint-resolved models are non-degradable.** A model resolved through `endpoint.base_url` SHALL NOT be substituted with a model not served by that same endpoint, on any path, including the headless path above. When such a model is unavailable: ask when an input facility exists; when none exists, halt that dispatch and record it, rather than rerouting it to a hosted model. Degrading a deliberately local model to a hosted one would move source code off the operator's machine, which is not recoverable after the fact.

**Analyzer probe (first-dispatch detection).** Preflight cannot enumerate the host's available models, so an unservable *model name* is detected only once the analyzer actually runs. When the analyzer returns (Step 2), compare the model named in its return JSON's top-level `served_model` field -- the analyzer's self-report of which model actually served it, exactly as `token_usage` is a self-report the orchestrator reads back -- against the model configured for the analyzer role. If they differ, open the availability gate above -- unless it has already been answered this run -- before dispatching any dev agent, and cache the answer into the model policy exactly as a preflight answer. `served_model` may be `null` when the analyzer had no reliable way to determine which model served it; a `null` value means the comparison is not possible, is NOT evidence of a mismatch, and MUST NOT by itself open the availability gate.

**Print the resolved map once**, in the established form:

    Model policy: <setting>: <value> (from <flag | .plan-runner.yml | default>).

One line per resolved role or tier entry whose source is not the built-in default.

**Mid-run degradation.** A configured model that becomes unavailable after the gate has already been answered degrades to the closest available model (or halts, per the endpoint exception above) and is recorded as a substitution -- it does NOT open a second gate.

**Persistence.** The resolved map, its provenance, the endpoint health, the consent answer, and every substitution persist as `model_policy` in `run-state.json` (Step 3's checkpoint write), matching `run-state.schema.json`'s optional `model_policy` object -- including `models.endpoint.roles`, so a rehydrated run still knows which roles are endpoint-bound. When a run resumes (R.5) or relays into a new phase (Step 3-bis.0), rehydrate `model_policy` from run-state rather than re-resolving the configuration or re-asking the gate. **Endpoint health is the one exception to "rehydrate, don't re-resolve":** re-probe it, and the `curl` check, fresh at a resume or a phase relay (an endpoint healthy at run start may be dead after a relay, and the reverse), and print the endpoint role map again from the rehydrated `roles` list. A re-probe failure at resume/relay is handled exactly as a first-run preflight failure: named, never substituted for an endpoint-bound role.

**Manifest recording.** When an agent is dispatched, record its resolved model in the manifest entry for that agent (`resolved_model`, alongside the existing `agent_source`), and any substitution as `model_substituted: {configured, dispatched, reason}` or `null`. When the agent is endpoint-bound, also record `dispatch_mechanism: "endpoint"` (`"host_subagent"` for every subagent/teammate dispatch, including a project agent) so the manifest carries which process actually made the call, not merely which label was configured.

**Codex parity.** The same `models:` block, read the same way, applies on the Codex backend: the resolution chain above is unchanged, tier words and raw identifiers are passed to whatever the host understands, and degradation follows the same closest-available rule. No client-specific key is required. This includes endpoint dispatch: the HTTP dispatch driver is invoked identically on both backends (skill-relative script resolution, above), and the eligibility check, curl probe, endpoint role map, and non-degradable-endpoint exception all apply without a client-specific branch.

**Honesty invariants, unweakened.** This feature never changes what counts as a verifier verdict: the verifier-coverage gate stays upstream of the PR step, and a model substitution never integrates or closes a task whose verdict is outstanding. The orchestrator does not self-verify because a substitution occurred, and token accounting for a substituted agent remains exactly as best-effort as for any other.

No credential value -- from `api_key_env` or anywhere else -- is ever printed to the console or persisted to `.plan-runner.yml`, the manifest, or `run-state.json`. Only the environment variable's name appears. This extends to the HTTP request path itself (Step 4a): the request-spec file that carries the resolved `Authorization` header lives only in a host temp location outside the cycle directory, is never a retained cycle artifact (never copied into `returns/`, a bug report, a manifest entry, or a return JSON), and is removed once the driver's attempt(s) finish -- the driver itself already deletes its own request-body temp file the same way. No step of composing, dispatching, retrying, or logging that request ever prints the resolved value; only the environment variable's name ever appears anywhere this rule already covers.

## Step 3-bis: PHASE EXECUTION (driver, modes, and boundaries)

This step decides *which session* runs the scheduler and *what happens at each phase boundary*. The scheduler itself (Step 4) never changes: the six-task ceiling, path reservations, per-task gates, independent verification, bounded repair, and central integration hold identically in an unphased session, a relay phase runner, and a stop-mode session.

**Unphased passthrough.** If `phasing_active` is false, this step is a no-op: run Step 4 (4.0 through 4g) in this session until every task is terminal, then Step 4j (final verification), then Step 5.

A **phase** is one scheduler session, numbered `P` = the count of `checkpoint` events already in `events.jsonl`, plus one -- so a resumed or recovered session never reuses a number (and never overwrites an earlier `suite-phase-<P>.log`). It ends at a **phase boundary**: when `dag.integrations_completed` has advanced by `max_integrations_per_phase` since the session started, or when every task is terminal (`integrated` or `blocked`), whichever comes first. At a boundary the scheduler dispatches no new task, drains only already-active task pipelines to durable state (Step 4i), runs the boundary suite (Step 4h), and writes a `checkpoint` event. Waves are not counted anywhere.

### 3-bis.1. Resolve the effective execution mode

`phase_mode` (from Step 1d-quinquies) is `relay`, `stop`, or `auto`. Resolve the mode that governs this run, in this precedence:

2. **Explicit mode.** Else if `phase_mode` is `relay` or `stop`, set `effective_mode = phase_mode` (a flag or the yml chose it explicitly).

3. **Adaptive default.** Else (`phase_mode == "auto"` -- no explicit mode configured), resolve by the estimated `phase_count`:
   - If `phase_count > auto_stop_phases`: `effective_mode = "stop"` -- the large plans that motivate phasing default to the full process reset.
   - Else (`phase_count <= auto_stop_phases`): `effective_mode = "relay"`.

   Print the one-line explanation, exactly one of:

   `Adaptive mode: <phase_count> phases <= auto_stop_phases (<auto_stop_phases>) -- relaying (context reset per phase).`
   `Adaptive mode: <phase_count> phases > auto_stop_phases (<auto_stop_phases>) -- stopping at each boundary (full process reset).`

Store `effective_mode`. Branch: `relay` -> 3-bis.2; `stop` -> 3-bis.3.

### 3-bis.2. Relay mode -- phase-driver loop

The invoking session is a thin driver. In relay mode it NEVER runs the scheduler itself; each phase runs in its own fresh-context phase-runner subagent, and the driver holds only run-state pointers plus one phase summary at a time. Driver-side nesting stays at a constant depth regardless of `phase_count` (driver -> phase runner -> task agents), never a phase-to-phase chain -- a chain would nest one level per phase and hit the platform's depth cap on large runs (ADR-0003).

Resolve this active `SKILL.md` to an absolute path once. Then repeat, with `P` counting from 1, while the run-state still holds a task that is not terminal:

1. **Guardrail check at the boundary.** Before dispatching phase `P` when `P > 1`, apply the relay wall-time guardrail (3-bis.4). If it trips, force a stop boundary here and end the session -- do NOT dispatch the next phase.
2. Dispatch a fresh-context general subagent -- the same self-contained handoff mechanism as the Step 6 fix-plan re-run -- with this prompt:

```
You are executing the Plan Runner run skill as a phase runner in a fresh session.

Read the complete skill instructions at <absolute path to this run SKILL.md>.
Treat them as the active instructions and execute them with this invocation input:
  --phase-runner <absolute run-state path> --phase <P><append " --no-project-agents" when no_project_agents_flag is true>

Everything else -- the task graph, durable task state, backend, TDD state -- is already
on disk in the cycle directory. Read it fresh. Run the scheduler until the next phase
boundary (Step 3-bis.0), then return the single phase-summary JSON.
Do not aggregate, do not open a PR, do not run any terminal step.
```

3. Wait for the phase-runner to return. Parse its phase-summary JSON. **A returned runner is not running.** A subagent that has returned cannot be woken by any background command, monitor, or timer it armed, so a return that does not parse as a phase-summary at all -- a progress note, "waiting on the gates", a truncated message -- is a **premature return**, never a reason to wait or to report the phase as "still running". (A summary that parses with `status: interrupted` is NOT premature: the runner finished and reported that it could not reach a boundary; it takes the interrupted path below.) Recover at once, without asking: when the host can message a returned subagent, continue the SAME runner (tell it that it returned before finishing phase `<P>`, that nothing will wake it, and to resume at its first incomplete step, blocking on any outstanding gate or return file in the foreground); otherwise stop any gate process it left running (a `gates/*.pid` with no matching `.exit`) and dispatch a fresh phase runner for phase `<P>`, which continues from the durable task state (Step 3-bis.0). Allow at most two recoveries per phase and print one line for each (`Phase <P> runner returned early (<first words of its message>) -- recovering (<n>/2).`). When the recoveries are exhausted, or `status` is `interrupted`, treat the phase as interrupted: the run-state already records every task's durable state, so offer resume in-session or stop with the resume invocation (the resume path). Do NOT drive later phases over an interrupted one.
4. Record the phase summary for the terminal Run Report. The driver keeps ONLY this summary -- never the phase's per-task agent returns or transcripts.
5. Tear down the phase-runner subagent with the host-native stop facility once its summary is captured; it must not idle after returning.
6. Print the compact intermediate phase summary (the **Intermediate phase summary** block in the Token accounting section; never the full Run Report) and continue to phase `P+1`.

When every task is terminal (and the guardrail has not tripped), proceed to Step 4j (final verification, unless the manifest already records a non-`pending` result) and then Step 5. The driver never dispatched a task agent or verifier itself, so it carries no task-level context into aggregation.

### 3-bis.3. Stop mode -- clean session boundaries

Stop mode fully resets the host process at each boundary: each session runs exactly ONE phase directly in its own context, then ends the session, and a fresh OS process resumes the next phase. This is the complete memory fix -- relay resets context but not host-process heap; stop resets both -- and is what the teams backend and large runs use.

1. Run Step 4 directly in this session until the next phase boundary.
2. At the boundary, confirm the run-state reflects it (every task this session touched is durable; `dag.resume_task_id` names the next pending or ready task; a `checkpoint` event is written).
3. Then:
   - **Tasks remain:** print the compact phase summary (the **Intermediate phase summary** block, not the full Run Report) followed by a copy-pasteable resume invocation, and end the session cleanly (STOP). Do NOT run Step 5 or any terminal step -- the fresh resumed process runs the next phase.

```
Phase <P>/<phase_count> complete. Stopping here for a full process reset before phase <P+1>.
Resume with:
  Claude Code:  /plan-runner:run --resume <absolute run-state path>
  Codex:        $plan-runner:run --resume <absolute run-state path>
```

   - **Every task is terminal:** do NOT stop. Proceed to Step 4j (final verification) and Step 5, then the terminal steps (Step 7-bis, Step 8, Run Report) run in this session exactly as on an unphased run. Step 5 reads every task's bug report from disk, so it needs no earlier-phase context.

The `--resume` flag, pre-flight auto-detect, and crash recovery that re-enter the scheduler are the resume machinery; a stop boundary here only ensures the run-state is current and prints the invocation. The guardrail-forced stop (3-bis.4) reuses this exact boundary and invocation.

### 3-bis.4. Relay wall-time guardrail

Relay keeps the driver's context lean but does NOT reset the host process, so a long relay run can still creep toward the process-memory envelope. Bound it by wall-time, not by hoping payload caps suffice. While relaying (3-bis.2), at every phase boundary -- after phase `P` completes and before dispatching phase `P+1` -- compare elapsed wall-time since this session's run start (`t_start`, Step 1) against `relay_max_minutes`:

- If `(now - t_start)` in minutes is `<= relay_max_minutes`: continue to the next phase's relay dispatch.
- If it exceeds `relay_max_minutes`: force a **stop-and-resume** at this boundary. This is an early stop boundary that reuses the stop machinery (3-bis.3): the run-state is already current, so print the reason and the copy-pasteable resume invocation and end the session (STOP). The fresh resumed process continues from the durable task state; its mode re-resolves, and if it relays again its own `t_start` restarts the guardrail clock.

```
Relay guardrail: <elapsed>m elapsed since run start exceeds relay_max_minutes (<relay_max_minutes>m).
Forcing a stop at the phase <P>/<phase_count> boundary for a full process reset.
Resume with:
  Claude Code:  /plan-runner:run --resume <absolute run-state path>
  Codex:        $plan-runner:run --resume <absolute run-state path>
```

## Resume and crash recovery

Every run checkpoints to `run-state.json` (written in Step 3, rewritten at every task state transition in Step 4). Resume re-enters an interrupted run -- a planned `stop`-mode boundary, a guardrail-forced stop, or a machine crash -- from its durable task state. Resume reads state ONLY from `run-state.json` plus the on-disk artifacts it points at (the task graph, `events.jsonl`, the manifest, returns, bug reports); it never infers progress from Git history alone, and it must never redispatch a task whose state says `integrated`. Two entry points reach this machinery:

- **Explicit `--resume [path]`** (`resume_flag` is true): a resume invocation carrying no plan path; Step 1 routes here instead of the fresh pre-flight.
- **Pre-flight auto-detect** (Step 1a-0 on a normal fresh run): an incomplete run-state is found and the user accepts the resume offer (R.1).

Both entry points run Step 1b-bis's Git and worktree checks before anything else: a checkpoint is useless without them.

### R.1. Locate the run-state (explicit path, bare scan, or auto-detect)

Resolve `run_state_path`:

- **Explicit path** (`resume_path` is set): use it directly as `run_state_path`.
- **Bare `--resume`** (`resume_flag` true, `resume_path` unset) **or the Step 1a-0 auto-detect scan**: scan for resumable run-states:
  1. Find every `run-state.json` under `<docs_base>/plan-runner/` (Glob `<docs_base>/plan-runner/**/run-state.json`), using `docs_base` resolved in 1a-minus. If `docs_base` differs from `docs`, ALSO glob the legacy `docs/plan-runner/**/run-state.json` and union the two result sets, de-duplicating any path that appears in both (the two glob roots always differ inside this branch, since it only runs when `docs_base` differs from `docs`; a collision is not expected but the de-dup guards against aliasing -- e.g. a symlink or a case-insensitive filesystem -- without weakening the union). This keeps runs started before a repo adopted a different `docs_base` -- or runs from a repo whose base legitimately is `docs` -- discoverable either way.
  2. Read each. Keep those that parse AND whose `overall_status` is `active` AND that carry a `dag` member with at least one task that is not terminal, or whose manifest `dag.final_verification.status` is still `pending`. Skip every `complete` or `abandoned` run-state -- **abandoned run-states are never re-offered or resumed.** (`active` is the only resumable status: every write site sets `active`, `complete`, or `abandoned`.)
  3. If none qualify: for a **bare `--resume`**, print `No resumable run found under <docs_base>/plan-runner/.` (or, when the legacy path was also scanned, `No resumable run found under <docs_base>/plan-runner/ or docs/plan-runner/.`) and STOP (the user asked to resume; do not silently start fresh). For the **Step 1a-0 auto-detect**, return to Step 1a and continue the fresh run silently.
  4. Otherwise pick the most recent by `updated_at` as the candidate (note in the offer if others also exist). For a **bare `--resume`**, set `run_state_path` to the candidate and continue to R.2. For the **Step 1a-0 auto-detect**, print the offer:

```
Found an incomplete plan-runner run you can resume:
  <run_state_path>
  plan:    <plan_path>
  tasks:   <integrated>/<T> integrated, <blocked> blocked; next: <dag.resume_task_id or the first ready task>
  updated: <updated_at>

[Y] resume this run
[n] start a fresh run on <given plan path> (marks the incomplete run abandoned)

(Y/n)
```

  On `Y` (or empty default): set `run_state_path` to the candidate and continue to R.2. The plan path given on the fresh invocation is ignored -- all state comes from the run-state. On `n`: **mark the candidate `abandoned`** -- set its `overall_status` to `abandoned`, rewrite `updated_at`, write it back -- so it is not re-offered on later runs, then return to Step 1a and continue the fresh run on the given plan.

### R.2. Load and validate the run-state (corrupt or missing)

Read `run_state_path`. If the file does not exist, does not parse as JSON, or is missing any required field (`plan_path`, `plan_content_hash`, `overall_status`), print the failure and offer a fresh run -- **never infer state**:

```
Cannot resume: run-state is missing or unreadable.
  <run_state_path>
  reason: <file not found | JSON parse error: ...  | missing field: ...>

Start a fresh run instead with:
  Claude Code:  /plan-runner:run <path-to-plan.md>
  Codex:        $plan-runner:run <path-to-plan.md>
```

Then STOP. If `overall_status` is `complete`, print that the run already finished and STOP. If `overall_status` is `abandoned`, print that this run-state was abandoned and STOP -- abandoned run-states are never resumed.

Required fields for this check are `plan_path`, `plan_content_hash`, `overall_status`, and `dag`. A state that parses continues to R.3, which validates it in full before anything is dispatched.

### R.3. Validate the checkpoint against its branch, graph, and events

Derive `cycle_dir` from the parent of `run_state_path`. Run every check below before creating a worktree or dispatching an agent. On any failed check, print the exact branch, graph, state, or event-evidence failure and STOP; the checkpoint remains intact for operator repair or inspection. Never downgrade, repair, or reinterpret a checkpoint by guessing.

1. **State.** Validate the entire run-state against `run-state.schema.json`; require the complete `dag` object, `dag.mode == "dag"`, `dag.branch_owned == true`, a non-empty `base_ref`, a non-empty `integration_branch`, a positive `max_integrations_per_phase`, and one complete durable task record for every graph task. A missing field or any schema failure is a safe stop.
2. **Branch.** Validate the run-owned branch without changing the operator checkout. Require `refs/heads/<dag.integration_branch>` to exist, require `base_ref` to resolve, and require `base_ref` to be an ancestor of the integration branch. Locate the dedicated integration worktree with `git worktree list --porcelain` (the entry whose branch is that ref): reuse it when its directory still exists; otherwise `git worktree prune`, recreate it in a host temp location, and re-apply the Step 1c-ter bootstrap using `dag.worktree` and the gate budgets from the cycle-root manifest (load them first -- R.5); do not check out, reset, merge, or commit on the operator branch. A missing branch, ref mismatch, non-owned branch, or worktree collision is a safe stop before dispatch.
3. **Graph.** Read `<cycle_dir>/task-graph.json` and validate it against `task-graph.schema.json` plus Step 2's uniqueness, dependency, and cycle checks. The graph task-ID set and each task's `depends_on` list MUST exactly match `dag.tasks`; every durable record must reference its graph task, and no graph task may lack a durable record. Validate every `integrated` record has its required integration/verification evidence and every `blocked` record has its durable block reason. Do not add, remove, or infer task edges, records, or completion from Git history.
4. **Events.** Resolve `dag.events_path` canonically and require it to be the cycle's `events.jsonl`, not a path outside the cycle directory. Parse every non-empty JSONL line and validate it against `task-event.schema.json` in append order. Require matching `base_captured` and `integration_branch_created` evidence for the recorded base ref and integration branch. Every task event must name a graph task, and durable outcomes must have matching evidence: each integrated task has a `task_integrated` event carrying its `integrated_commit`; each blocked task has a `task_blocked` event; each attempted in-flight task has its dispatch/retry evidence. Events are audit evidence only: a missing or conflicting line, or a malformed JSONL line, is a safe stop before dispatch, never an instruction to manufacture state or mark a task complete.
5. **Re-entry.** If all evidence validates, append exactly one `resume` event and atomically persist the unchanged authoritative task state. The ready set is recomputed only from records whose status is `pending` or `ready` and whose dependencies are `integrated`. `integrated` tasks are terminal and are excluded from every ready-set, reservation, worktree, and dispatch operation; blocked tasks stay blocked and prevent dependent eligibility. Preserve `dispatched`, `verifying`, and `retrying` records and continue each from its durable worktree, return, and verification artifacts at the pipeline step its artifacts prove it reached (Step 4): a return file that exists is captured, a verdict file that exists is captured, a missing verdict is re-requested. A `dispatched` or `retrying` record with no return file for its current attempt lost its agent with the old session: reset its recorded worktree to that attempt's starting point (the task's `base_commit` for attempt 1 or a re-execution; attempt 1's `produced_commit` for a same-worktree repair -- never wipe the commit a repair builds on), recreating the worktree there if a temp purge removed it, re-dispatch that same attempt, and append a `task_dispatched` event with `reason: redispatch after lost session` -- this consumes no repair budget, because no verdict was ever produced. Never create a replacement dispatch for a verdict-driven retry until the corresponding `task_retry_requested` state and event are durable.

A pre-3.0.0 checkpoint -- a run-state with no `dag` member, written by the removed wave executor -- cannot be resumed. Print `Cannot resume: this checkpoint was written by the wave executor, which was removed in plan-runner 3.0.0. Start a fresh run on its plan.` and STOP. A `dag` member that is present but malformed prints `Cannot resume: malformed DAG checkpoint.` with the validation error and STOPs.

### R.4. Plan-drift guard

Re-hash the plan file at `plan_path` (same tool and normalization as Step 3) and compare it to the stored `plan_content_hash`. On a mismatch -- or if the plan file is now missing -- warn and **require explicit confirmation** before continuing against the already-validated task graph:

```
Plan file has changed since this run was checkpointed:
  <plan_path>
  checkpoint hash: <stored plan_content_hash>
  current hash:    <current hash, or "file missing">

Resuming runs the task graph as validated at checkpoint time; it does NOT re-analyze the
edited plan. Continue against the checkpointed task graph anyway? (y/N)
```

The default is No. On anything but an explicit `y`, STOP and suggest a fresh run to re-analyze the edited plan. Only when the hash matches (or the user explicitly confirms) proceed to R.5.

### R.5. Restore run variables and hand to phase execution

Derive every resumed variable from the run-state, the cycle-root manifest, and their location, so nothing depends on Step 1's fresh-run computation:

- `cycle_dir` = the parent directory of `run_state_path`. Do NOT recompute cycle numbering or re-derive any path from Step 1 variables.
- `cycle_n` = the manifest's `cycle`; `run_id` = the one on the `base_captured` event. `phasing_enabled` and `phase_mode` = the run-state's `invocation_flags`.
- `backend`, `tdd_enabled`, `phase_mode`, and `model_policy` = the values recorded in the run-state. `model_policy` rehydrates (Step 1d-septies) rather than re-resolving the `models:` configuration or re-opening the availability gate; it is absent only when `models_enabled` was false.
- When `tdd_enabled`, load the **test command** (both forms), `baseline_failing`, `baseline_state`, `baseline_suite_seconds`, and the resolved `gates` settings from the cycle-root `manifest.json` `tdd` block, and `dag.worktree` and any top-level `role_delivery` alongside them -- the same source the phase runners read, so an original `--test-cmd` survives the resume and the driver and its runners never diverge. **Never re-capture the baseline on resume.** The baseline means "failing before this cycle's work began"; a baseline re-captured mid-cycle would absorb every integrated task's regressions as pre-existing, and they would never be reported.
- Re-detect host facilities that are not persisted: `context7_available` per Step 1d. Re-resolve `project_agents_enabled` and rebuild `agent_inventory` / `routing_directives` per Step 1d-sexies -- also not persisted. The `--no-project-agents` flag is not recorded in the run-state, so repeat it on the resume invocation (or set `agents.project: false` in `.plan-runner.yml`) to keep the opt-out across a resume. Re-resolve `auto_stop_phases` and `relay_max_minutes` from `config_text` -- loaded by Step 1a-minus-bis, which an explicit `--resume` runs like any other invocation -- per Step 1d-quinquies; `max_integrations_per_phase` comes from the run-state.
- Record `t_start = $(date +%s)` for this resumed session (the relay guardrail clock restarts per session, Step 3-bis.4).

The operator's checkout needs no decision on resume: plan-runner never wrote to it, and an interrupted task's partial work lives only in its disposable worktree.

Set `overall_status` to `active` in the run-state, rewrite `updated_at`, and write it back. If every task is already terminal, skip the scheduler: proceed to Step 4j (final verification, unless the manifest already records a non-`pending` result) and Step 5. Otherwise set `phasing_active` from the count of tasks that are not yet terminal (Step 3's rule) and enter Step 3-bis (skip Step 3's display -- the graph is already on disk), which re-resolves the effective mode (Step 3-bis.1) and runs the scheduler from the durable task state. Aggregation, the verifier-coverage gate, and every terminal step (Step 5, Step 7-bis, Step 8, the Run Report) still run only once, after every task is terminal, exactly as on a non-resumed run.

## Step 4: TASK EXECUTION (dependency-ready scheduler)

The scheduler honors the `backend` chosen in Step 1d-ter; the backends differ only in how task agents are dispatched and how their results are collected (4a). Everything else is identical on both.

**One task's pipeline.** Each task moves through the same steps, independently of every other task. Nothing here waits for a wave, because there are none:

1. 4a -- reserve the task's paths, create its worktree, dispatch its dev or test-author agent.
2. 4a-bis -- capture the return and tear the agent down. 4b -- commit the task's work in its worktree and check the complete diff against declared ownership.
3. 4c -- run the task's gates in its worktree. 4d -- request independent verification of the task commit.
4. 4e -- decide from the evidence: integrate, repair once, or block. 4f -- central integration onto the run-owned branch.
5. 4g -- record the outcome durably; its dependents become ready at once.

Print, once, when the scheduler starts in this session:

```
[Phase 2/4] Scheduling <remaining> tasks (up to 6 at once)...
```

Record `t_tasks_start = $(date +%s)`; add this session's scheduling time to the manifest's running `task_execution_seconds` when the session ends.

### 4.0. The scheduling loop

Repeat until every task is `integrated` or `blocked`, or a phase boundary is reached (Step 3-bis):

1. **Read the durable task state fresh** (`run-state.json`), and validate it. A task is `ready` only when it is pending/ready and every declared dependency has status `integrated`. If a dependency is blocked, mark the dependent `blocked` with a dependency-derived reason (`blocked dependency: <task_id>`) and append a `task_blocked` event (its manifest entry records `attempts: 0` and, having never had a worktree, the run's `base_ref` as its `base_commit`); do not speculate or dispatch it.
2. **Select ready tasks independently, without waiting for unrelated active or ready work.** Keep at most **six active dev tasks total** -- a task is active from its first dispatch until it reaches a terminal state, and a task being repaired is still active. Advance `retrying` and `verifying` records before selecting anything new: they already hold a place under the ceiling and their paths stay off-limits to every other task. Do not select a task whose `owned_files` overlaps an active task's declared ownership (including declared shared files); leave it ready for a later scheduler pass. Prefer, among the ready tasks, the one with the most transitive dependents: work on the critical path first, since everything behind it is waiting.
3. **Start each selected task's pipeline** (4a) and keep control. Dispatch task agents and verifiers asynchronously (as background subagents, or as teammates) whenever the host allows it, so the scheduler can start and advance other tasks while they work. On a host whose only dispatch is blocking, dispatch the entire selected set in one parallel batch and treat the batch's return as the scheduling point: the schedule degrades to dependency-correct batches, and every rule here still holds.
4. **Wait for progress in the foreground, then advance whatever progressed.** Progress is a file: a dev agent's `return_file`, a verifier's `return_file`, an integrator's `return_file`, or a gate's `<log>.exit`. Block until at least one outstanding progress file exists (consecutive foreground waits, each bounded by the host's command limit, exactly as **Gate discipline** rule 3 waits on a gate), then advance every task whose file has appeared by one pipeline step, and return to step 1. **Never end your turn while any task is active**: a completion notification is a convenience, and a scheduler that is itself a subagent is never woken by one. A task whose agent has produced no return file within a generous bounded wait is treated per 4a's bounded-wait rule, never waited on forever.

**Task states.** `pending` -> `dispatched` (attempt 1 in flight) -> `verifying` (its verifier is dispatched; `produced_commit` is set) -> `integrated`, or -> `retrying` (attempt 2 in flight: the record keeps attempt 1's verification artifacts and its worktree) -> `verifying` -> `integrated` or `blocked`. These are exactly the shapes `../../schemas/run-state.schema.json` validates per status; persist each transition before acting on it.

At every state transition append exactly one JSONL event validated by `../../schemas/task-event.schema.json` (`paths_reserved`, `task_dispatched`, `task_retry_requested`, `task_verified`, `task_integrated`, `task_blocked`, `paths_released`, `checkpoint`, `resume`, or `final_verification`), and rewrite the task's record in `run-state.json` atomically before moving to the next task. Events are append-only; do not rewrite, reorder, or use them to manufacture missing state. Persist state and event evidence before removing a task worktree.

### 4a. Reserve, isolate, and dispatch the task

**Reserve the task's paths first.** Before transitioning the task record to `dispatched` -- a first dispatch, a repair, or a re-execution alike -- atomically persist that transition together with a schema-valid `paths_reserved` event (`reservation_id`, `task_id`, `attempt`, and `paths`, the normalized union of `owned_files` and `shared_files`), per `../../agents/plan-integrator.md` step 1. A repair or re-execution reuses this same gate and must have durably recorded the prior attempt's `paths_released` release (4e) before this fresh reservation is created. While a reservation is active no other writer whose paths intersect it may be dispatched.

**Create the task's worktree (attempt 1, and a re-execution).** A same-worktree repair (4e) skips this paragraph entirely: it keeps attempt 1's `worktree_path` and `base_commit`, and its agent works on top of attempt 1's `task_commit`, so `base_commit..HEAD` is still exactly the task's own work. Otherwise set `base_commit` to the current integration branch commit, which includes every integrated dependency. Create a disposable task branch and a task worktree for it at `base_commit`, outside the repository, in a host temp location, and apply the Step 1c-ter bootstrap (link the shared directories, run `setup`). Record `worktree_path` in the task state. Only once the reservation is durable, append `task_dispatched`, then dispatch. Do not permit a task agent to mutate the integration worktree or the operator checkout.

**Attempt labels.** A task's first dispatch is attempt `1`, its single repair or re-execution is attempt `2` (the schema caps `attempts` at 2). Every per-attempt artifact carries the label `<task_id>-a<attempt>`: the dev return (`returns/<task_id>-a<n>.json`), the verdict (`returns/<task_id>-a<n>-verifier.json`), the gate logs, and the ownership evidence.

**Select the bundled role by the task's `role` field** (in classic / non-TDD runs there is no `role` -- treat every task as an impl/standalone dev agent served by `plan-dev.md`) and deliver it per **Portable role loading** -- by absolute path, never pasted:

- `role: "test-author"` -> `../../agents/plan-test-author.md`; include the resolved `test_command` so it can match the test framework/style and confirm its red.
- `role: "impl"` -> `../../agents/plan-dev.md`; include a `TESTS TO SATISFY` block listing the task's `tests_to_satisfy`, and the resolved `test_command` so the agent can check its own work in its worktree before returning.
- `role: "standalone"` or no role (classic) -> `../../agents/plan-dev.md` with no `TESTS TO SATISFY` block.

**HTTP endpoint dispatch (dev and test-author only), checked before anything else in this step.** When `models.endpoint.roles` (Step 1d-septies) names this agent's pipeline role -- `dev` for an `impl`/`standalone`/classic agent, `test-author` for a test-author agent -- dispatch it by issuing an OpenAI-compatible chat-completions request to `models.endpoint.base_url` yourself, instead of a host subagent. Such an agent skips every remaining host-dispatch mechanic in this step below -- project-agent selection, the tool guard, prompt assembly, the per-backend dispatch, and the rogue-commit guard (there is no shell on the model's side to rogue-commit with) -- and its teardown (4a-bis) is a no-op, since there is no resident process to release. It still counts toward the six-active-task ceiling, still holds its path reservation, still writes only inside its task worktree (invoke the driver with that worktree as its working directory, so every owned path resolves there), and still commits (4b), runs its gates (4c), and is graded by a host-dispatched verifier (4d) exactly like any other task: the mechanism differs, the invariants do not.

1. **Compose the request spec**, matching the driver's documented contract (`scripts/http-dispatch.js`): `base_url` and `model` from the resolved endpoint and model-policy map; `role` = the agent's pipeline role, informational only; `owned_files` = the task's declared owned files verbatim; `headers` = `{"Authorization": "Bearer <api_key_env value>"}` when `api_key_env` is set, read directly and never printed (Step 1d-septies credential rule); `budgets.max_tokens` and `passthrough` = `models.endpoint.request`, resolved in Step 1d-septies and otherwise left to the driver's own defaults. Write the spec to a file in a host temp location outside the cycle directory -- never under `returns/` or anywhere else a cycle artifact is retained.
2. **Compose `messages`.** A system message carrying the bundled role's domain-guidance text, pasted -- an endpoint model has no tools to read a role file with, so this is the one bundled dispatch that cannot go by path (`plan-dev.md`'s Domain half for a `dev` role, `plan-test-author.md`'s for `test-author` -- see "Prompt assembly" below -- minus the Dev Return Contract section: an endpoint-bound agent is never asked to return JSON itself, so that contract does not apply to it) plus an explicit output-format instruction: respond with ONLY one fenced code block per file, each preceded by that file's repository-relative path on its own line, covering every owned file to write, and nothing else -- no prose, no JSON, no return object; the exact format `scripts/fenced-blocks.js` parses. A user message carrying, in order: the task excerpt (read from `plan_path` at `task_excerpt_lines`, exactly as a subagent dispatch would), its acceptance criteria, the conventions sample (next), the resolved `test_command` for a test-author agent, and the full content of every owned file that exists on disk, each preceded by its repository-relative path -- an owned path that does not yet exist on disk is named instead as a file to create, never omitted (the common case for a test-author task whose owned files are all new).
3. **Select the conventions sample.** The orchestrator alone performs this selection -- neither the driver nor the parser ever consults the plan or the repository, by contract. Candidates are the repo's existing test files nearest the task's owned paths: same directory first, then the nearest ancestor directory containing test files, lexicographic within each tier. Take whole files only, nearest-first, until either 3 files or 32 KB total would be exceeded; a file that would cross either cap is dropped whole, never truncated. These files are read-only context, never members of the task's `owned_files`, so a returned block naming one is refused by the parser exactly as any other unowned path (step 8 below). **When every candidate is dropped by the cap, or none exist, the sample is empty**: say so plainly in the composed message (e.g. "No conventions sample available -- no nearby test files fit within the cap.") rather than silently omitting the section, and report it on this agent's dispatch line next.
4. **Print the dispatch line**, in the same place the existing host-dispatch provenance line prints:

       <agent_id>: served by endpoint (<base_url>)
       <agent_id>: conventions sample empty -- see request               [only when step 3's sample is empty]

5. **Invoke the driver**: `node ../../scripts/http-dispatch.js <request-spec> <response-record> <return-json>` (paths resolved as in "Portable role loading and host facilities"). The driver composes the body, calls `curl` with exactly one retry at a reduced completion budget on any failure -- a timeout, a non-2xx response, no parsable fenced block, or a block truncated mid-file all count -- writes every in-scope block to disk itself via the parser, and hands back a response record plus a partial return object. Delete the request-spec temp file once the driver returns, whether or not the call succeeded.
6. **Construct the return JSON yourself, never trusting model output.** Take `status`, `files_written`, `files_unexpectedly_modified` (always empty -- the parser never writes outside the owned set), `concerns`, `summary`, and `token_usage` from the driver's returned object verbatim: the model was never asked for a return JSON, so there is nothing of its authorship to distrust here. Fill in `agent_id`, `task_id`/`task_title`, and `context7_queries: []` yourself. Any field the TDD gates or the verifier consume from the task graph (an impl agent's `tests_to_satisfy`, a test-author's declared owned set) is carried over from the task definition unchanged, exactly as for a host-dispatched agent -- never read from anything the model returned. Write this constructed object to the task's `return_file` (`returns/<task_id>-a<n>.json`) and treat it as this agent's return for every purpose below (gates, the verifier prompt, the manifest): the orchestrator built it, not the model, so nothing about it is polled or re-validated.
7. **A failing retry is a durable failure, never a fallback.** When the driver's response record still carries an `error` after its one retry, this agent's `dev_status` is `BLOCKED` with that error in `concerns` -- exactly the shape a host-dispatched dev agent's `BLOCKED` return already takes -- and it flows through the same verify -> aggregate -> fix-plan -> re-run loop (4c/4d/Step 5) as any other blocked task. An endpoint-bound role is **never** rerouted to a host subagent or a hosted model on this or any other failure path -- a `curl` failure, a configuration error, or the non-degradable-endpoint exception (Step 1d-septies) -- because degrading it would move source code off the operator's machine, the one outcome this feature exists to prevent.
8. **Ownership is enforced by the parser, not by trust.** A block naming a path outside `owned_files` is refused and left unwritten by `scripts/fenced-blocks.js`; the refusal already reaches `concerns` via the driver's own return construction (step 6), so it surfaces to the verifier like any other dev-reported concern.

Every task agent -- endpoint-bound and host-dispatched alike -- is subject to the same path reservation (4a), the same six-active-task limit, the same per-task pipeline (dispatch -> commit -> ownership -> gates -> verify -> integrate), and the same verifier-coverage gate (Step 5.0) upstream of the PR step. **The verifier itself is never endpoint-bound**: `models.endpoint.roles` cannot name `verifier` (Step 1d-septies), so an endpoint-bound dev or test-author agent's work is always graded by an independent, host-dispatched verifier -- "no self-verify" keeps its force when the author is local.

**Project-agent selection (dev tasks only).** For each task being dispatched whose role is `impl`, `standalone`, or absent (classic), decide which definition serves its dispatch. Skip selection entirely and set `agent_source = "bundled"` when `project_agents_enabled` is false (Step 1d-sexies), when `agent_inventory` is empty, or when the task's `role` is `test-author`. **Test-author, verifier, and aggregator dispatches always use their bundled definitions, regardless of the inventory** -- the verifier (4d) and aggregator (Step 5) never consult it at all, which is what keeps verification independent of the code's author.

Apply these rules in order and stop at the first that resolves:

0. **Pinned to bundled.** If this task is pinned to bundled `plan-dev` -- its title is in the in-session `bundled_pins` set (set by the return-contract validation below), or its task prose / acceptance criteria say to dispatch it with the bundled `plan-dev` -- select none, before any rule below is considered.
1. **Explicit routing directive wins.** If a `routing_directives` entry's `applies_to` covers this task (the work it describes matches the task's title, its `owned_files`, or its acceptance criteria), select that entry's `agent_name`. An explicit "use agent X for Y work" directive in AGENTS.md or CLAUDE.md **overrides the conservative description match** below -- the repo's own docs are a stronger signal than any inference from a description.
2. **Conservative description match.** Otherwise select a project agent whose `description` **clearly covers** the task's domain: the description names the technology, layer, or file type this task works in. The bar is deliberately high -- **any doubt selects none.** If two agents plausibly fit, if the fit rests on a generic word ("code", "files", "implementation"), or if the match is anything short of clear, select none.
3. **Bundled fallback.** Otherwise select none: the task is served by the bundled `plan-dev.md` loaded above.

**Tool guard.** A selected project agent whose `tools` frontmatter is present and lists **neither `Write` nor `Edit`** cannot write files, so it is disqualified: log the disqualification and dispatch bundled `plan-dev` instead. **Never widen a project agent's declared tools to make it eligible** -- dispatch it with exactly the tools its own frontmatter declares, or not at all. An absent `tools` field means it inherits all tools and is eligible.

    Project agent <name> disqualified for <agent_id>: tools frontmatter has neither Write nor Edit -- dispatching bundled plan-dev.

Record the outcome for every dev agent as `agent_source`: `"project:<name>"` when a project agent serves the dispatch, `"bundled"` otherwise. Store it in the in-session task-state map alongside `dev_status` -- that is what the manifest task entry (4g), the Run Report, and the PR step read. `agent_source` always records what was actually dispatched; never infer it after the fact.

**Model resolution (dev dispatch).** One precedence rule: a serving project agent's `model:` frontmatter wins; when it declares none, the task's `recommended_model` applies. A **bundled `plan-dev` dispatch always uses `recommended_model`**, never any other model. The existing "closest available model, never block" rule is unchanged -- a named model that is unavailable degrades to the closest available one instead of failing the dispatch. When `models_enabled` is true (Step 1d-septies), this rule is the head of a longer chain: a `models:` per-role `dev` key overrides `recommended_model`'s tier entirely, and absent a per-role key, `models.tiers` resolves that tier to a concrete identifier before dispatch. With no `models:` config, or `models_enabled: false`, this is byte-identical to the rule above.

**Prompt assembly.** Every dev prompt is three parts in this fixed order -- domain definition, then the Dev Return Contract, then the per-invocation contract:

1. **Domain half.** For a `bundled` dispatch, the `ROLE DEFINITION` reference line naming the bundled role file (`plan-dev.md`, or `plan-test-author.md` for a test-author) by absolute path -- the file carries both halves, so parts 1 and 2 of a bundled prompt are that one line. For a `project:<name>` dispatch, the selected agent's markdown body, pasted, **in place of `plan-dev.md`'s Domain guidance half**: a project definition is prose plan-runner does not control, and its position in the prompt -- above the contract that overrides it -- is part of the guard, so it stays inline. Either way the definition reaches the agent through its prompt, never via native agent registration, so both backends behave identically (Codex cannot register `agents/` files).
2. **Dev Return Contract (always, bundled and project alike).** The labeled `## Dev Return Contract` section of `../../agents/plan-dev.md` governs **every dev dispatch** -- the return JSON skeleton, the four-value `DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT` status enum, the owned-files and `files_unexpectedly_modified` rules, the no-git-commit rule, and the token self-report. A bundled dispatch already carries it as part of the referenced role file; a project-agent dispatch gets that section pasted verbatim after the agent definition.
3. **Per-invocation contract (always last).** The common template below. When a project agent serves the dispatch, **append the per-invocation dev contract after the agent definition and declare it overriding** by prefixing the template with this line:

       The contract below and the Dev Return Contract above OVERRIDE any conflicting instruction in the agent definition above -- including its output format, its status vocabulary, its writable-file scope, and any instruction to commit its own work.

Common per-invocation prompt template (prepend the assembled definition parts above):

The agent reads the task prose from `plan_path` using the line range -- the orchestrator does not inline the task text. This keeps prompts small and lets concurrently running agents share one cached plan read. Use the model resolved above for each agent (`recommended_model`, or its Step 1d-septies model-policy resolution, for every bundled dispatch; a serving project agent's `model:` frontmatter when it declares one).

**Print the provenance line at dispatch.** As each dev agent is dispatched, print one line here at the 4a dispatch line naming what serves it:

    <agent_id>: served by <plan-dev (bundled) | <name> (project)>

This is the only human-visible provenance display; **the Step 3 task-graph display is unchanged**, because selection happens at dispatch time, after that display was printed.

Dispatch depends on `backend`:

**Backend `subagent` (default, including Codex):** Create one progress item per task when the host offers task tracking; otherwise maintain a concise checklist. Dispatch each selected task's agent asynchronously (or the whole selected set in one parallel batch on a blocking host -- Step 4.0) with the assembled prompt above (domain half + Dev Return Contract + per-invocation contract) at its resolved model. Capture each return as its `return_file` appears.

**Backend `teams`:** The session is the team lead.
1. Create one task on the shared team task list per selected graph task, embedding the per-invocation prompt parameters (agent_id, task_id, task_title, plan_path, task_excerpt_lines, task_worktree, owned files, acceptance criteria, role-specific blocks) in the task detail. List only tasks the scheduler has already selected, so every listed task is immediately claimable: dependency order is enforced by the scheduler (Step 4.0), never by team-list dependencies.
2. Spawn one teammate per selected task (honor the six-active-task ceiling), each receiving the same assembled definition as the subagent backend -- the serving domain half (the `ROLE DEFINITION` line for a bundled role, or the selected project agent's pasted body), the Dev Return Contract, and the overriding per-invocation contract -- at the model resolved above. Selection and embedding are identical on both backends. Teammates self-claim the listed tasks.
3. Read teammate progress from the task list / mailbox -- do NOT pull full JSON returns into the lead context until an agent's return is being captured. Each teammate's durable return is its `return_file` (`$cycle_dir/returns/<task_id>-a<n>.json`, from its dispatch prompt): poll for that file's existence (Step 4.0) and read the final JSON status from it. The task result / mailbox message is a convenience preview only -- never depend on retrieving it for correctness: `TaskOutput` cannot resolve a named background agent, and a `SendMessage` "resend your final JSON" request races the teammate's idle teardown and can go permanently unanswered. A return file that fails to parse may be a write caught mid-flight; re-read it once after a short pause before treating it as absent.

For each dev agent return (both backends) -- an endpoint-bound agent's return was already constructed, and written to its `return_file`, by the HTTP endpoint dispatch step above, with no progress item to update, so skip steps 1-2 for it and start at step 3:
1. Read the agent's `return_file` and parse the JSON; when the file is missing or unparseable, fall back to parsing the agent's final message / completion result. If both sources fail, treat as `{"agent_id": "<id>", "status": "BLOCKED", "files_written": [], "files_unexpectedly_modified": [], "context7_queries": [], "summary": "agent returned non-JSON output", "concerns": ["unparseable response"]}` and continue.
2. Update the corresponding progress item or fallback checklist entry to `completed`.
3. Record the dev_status in the in-session task-state map.
4. Capture the agent's token usage (see **Token accounting**) and store it in the task-state map keyed by `agent_id`. Append it to the manifest's durable `token_usage.by_agent` as `{"agent": "<task_id>-a<n>", "phase": "task", ...}`: harness completion usage first; when it is absent -- common for teammates on the `teams` backend -- fall back to the `token_usage` self-report in the agent's return JSON; record `tokens: null` only when both are missing. For an endpoint-bound agent there is no harness or self-report to check: use the response record's `usage` object directly, source `http_usage`, exactly as **Token accounting** describes.

**Return-contract validation (project-agent dispatches).** A dispatch whose `agent_source` is `project:<name>` was served by a definition plan-runner does not control, so validate its parsed return against `../../schemas/dev-return.schema.json` (resolved relative to this skill; use Python+jsonschema when available, otherwise a structural check: required fields present, `status` one of the four enum values, array fields are arrays) before accepting it. A bundled dispatch is not re-validated -- its role file is the contract. On a validation failure do NOT classify the agent `BLOCKED` and do NOT fill in, guess, or repair any field:

1. **Re-prompt that agent once, with the schema alone.** Continue its existing session (`SendMessage` to its returned agent id -- do not dispatch a fresh agent): "Your return did not validate against dev-return.schema.json. Return ONLY a single JSON object matching this schema, with no prose before or after, and write it verbatim to your return_file: `<schema text>`". Then re-read its `return_file` and re-validate.
2. **If the second return also fails,** record the dispatch exactly as it came back, keep its `agent_source`, and add one `return_contract_violation` bug to this task's bug JSON (4d), carrying the dispatch's `agent_source` in its evidence:

```json
{"bug_id": "<task_id>-bug-<n>", "severity": "P2", "category": "return_contract_violation", "title": "Project agent <name> return failed dev-return.schema.json twice", "file": "<agent's owned_files[0] or 'n/a'>", "line": null, "evidence": "agent_source: project:<name>; validation error: <the validator's message, truncated>", "expected": "A dev return matching dev-return.schema.json", "suggested_fix": "Dispatch task '<task_title>' with the bundled plan-dev next cycle; the project agent does not honor the Dev Return Contract."}
```

   Then **pin that task to bundled `plan-dev` for the next cycle**: add its `task_title` to the in-session `bundled_pins` set (selection rule 0 above, which also covers any re-dispatch later in this cycle) and state the pin in the bug's `suggested_fix`, so the aggregator carries it into `fix-plan.md` and the re-run dispatches the task bundled. **Never fabricate a return field to make a return validate** -- missing fields stay missing, `token_usage` stays null when the agent reported none, and the gap flows through the normal verify -> aggregate -> fix-plan loop.

**Bounded wait per task (both backends):** there is no barrier -- each task advances on its own return. If a task agent is stuck past a generous bounded wait (on the `teams` backend, the known task-status-lag issue), check its `return_file` first -- a parked or already-gone agent whose return file exists and parses HAS completed; capture it normally. Only when the return file is also absent, read the task worktree's state directly, treat the unreported agent as `BLOCKED`, print a warning, and continue that task's pipeline at 4a-bis -- the gap then flows through 4e's repair-or-block decision and the normal verify -> aggregate -> fix-plan loop rather than hanging the scheduler.

**Rogue-commit guard (both backends):** Dev agents are forbidden from committing, but one that disobeys leaves a clean worktree that makes its work look undone. Before treating any task agent as silent-failed (missing return, empty owned-file diff, no worktree changes) -- and before requesting any repair for it -- run `git -C "<worktree_path>" log --oneline <base_commit>..HEAD`. If commits appear, the agent rogue self-committed on its disposable task branch: the work counts as delivered, so do NOT treat the task as empty. Print a warning naming the task and the rogue commit SHA(s), record the SHAs in the task-state map, and let 4b use `base_commit..HEAD` as the task's range so the task verifier (4d) judges the content exactly as it would judge scheduler-committed work. A rogue commit can never reach the integration branch on its own: only 4f applies commits there. Judging by working-tree diff alone is not sufficient evidence that an agent did nothing.

### 4a-bis. Tear down the task agent

A finished task agent does not exit on its own -- it stays resident (an idle background task or an idle teammate) until explicitly stopped. As soon as its return has been captured, tear it down, before the task's gates run:

- **Backend `subagent`:** release or stop the subagent with the host-native facility when it remains resident; if it exits automatically, no action is required.
- **Backend `teams`:** stop the teammate with its agent ID (`name@team`) or bare teammate name.

Tear down every task agent regardless of `dev_status` (`DONE` or `BLOCKED`) -- a blocked agent still holds its process open. If `TaskStop` reports the task already gone, treat that as success. Teardown cannot lose a result: the agent's return is file-backed in `$cycle_dir/returns/`, which survives the stop. Do this per task, as each one returns -- never let finished agents idle until the run ends.

### 4b. Commit the task's work and check ownership

The scheduler, never the agent, commits a task's work -- in the task's own worktree, on its disposable branch, never on the integration branch:

```bash
git -C "<worktree_path>" add -A -- . ':(exclude)<each shared directory>'
git -C "<worktree_path>" commit -m "plan-runner cycle <cycle_n> <task_id>: <task_title>"
```

Set `task_commit` (the state's `produced_commit`) to the resulting HEAD. If the agent rogue self-committed (4a's guard), the range `base_commit..HEAD` is still the task's complete work: commit whatever remains unstaged, if anything, and use the resulting HEAD. If the range is empty (nothing changed -- a `BLOCKED` agent, or a fix that was already in place), record `task_commit` = `base_commit` and carry on through every step: the ownership artifact is an empty diff with conformance `PASS`, the gates still run (they are what proves an already-satisfied task), and the verifier still judges the criteria.

**Ownership conformance (complete diff, first of two checks).** Write the complete, rename-aware diff of `base_commit..task_commit` to `$cycle_dir/ownership/<task_id>-a<n>.txt` (`git diff --name-status -M -C`). Every changed path -- added, deleted, renamed, copied, generated, or shared, both sides of a rename or copy -- must be declared in the task's `owned_files` or `shared_files`. This is a set comparison, not a judgment: record `ownership_conformance: PASS` or `FAIL` with the undeclared paths listed in the artifact. A `FAIL` does not stop the pipeline here -- the evidence goes to the verifier, which files the `scope_drift` finding, and 4e treats an ownership `FAIL` as a blocking finding whatever its severity label. Never silently discard an undeclared write and never widen ownership to fit it.

### 4c. Run the task's gates (only if tdd_enabled)

If `tdd_enabled` is false, skip this step (classic pipeline): `deterministic_checks` is `n/a`, and ownership conformance is the only mechanical check the task gets.

Every gate command runs under **Gate discipline** (file-backed log, time budget, foreground wait), **inside the task's worktree** -- the only tree that contains this task's work and nobody else's unfinished edits. There are **No inline retries** of a gate: a failure is recorded as file-backed evidence for the verifier, and what happens next is decided once, in 4e. These gates run unchanged for an endpoint-bound agent: they inspect the files the fenced-block parser wrote into the worktree, exactly as they would inspect a host subagent's edits, with no branch on `dispatch_mechanism` anywhere in this step.

**Gate evidence is a pointer, never a paste.** A task's `captured_test_output` -- the field the verifier prompt carries (4d) -- is a short mechanical header: one line per gate run giving `cmd`, `exit`, `result`, the parsed test count, and `log: <absolute path>`. The verifier opens the logs itself. The orchestrator never reads a whole log into its context and never re-types one into a prompt, so a task's evidence costs the same few lines whether its tests printed forty lines or forty thousand.

**Test-author task (role: test-author) -> RED gate:**
1. For each file in the agent's reported `test_files`, run the single-file test command (substitute `{file}`) into `$cycle_dir/gates/<task_id>-a<n>-red-<k>.log`.
2. Record `red_run` = `{cmd, exit, result: exit != 0 ? "FAILED" : "PASSED", valid_red: null, log}` (`result: "TIMEOUT"` when the budget expired). Leave `valid_red` null here -- the orchestrator cannot tell a genuine failure (import / not-implemented / assertion) from an invalid one (syntax / collection error) without analysis. The red-gate verifier (4d) makes that call; backfill `valid_red` in the manifest when that verdict is captured. A red gate that PASSED (exit 0 -- the orchestrator detects this directly) is an **invalid red**: set `valid_red: false` now.
3. The task's deterministic check is `PASS` when every red run executed tests and FAILED (the expected red), `FAIL` on an invalid red, and `UNVERIFIABLE` on a `TIMEOUT` or `BUILD_FAILED`.

**Impl task (role: impl) -> GREEN gate:**
1. For each file in the task's `tests_to_satisfy`, run the single-file test command (substitute `{file}`) into `$cycle_dir/gates/<task_id>-a<n>-green-<k>.log`.
2. Parse the runner-reported executed/collected test count from each log's summary line (`N passed`, `ran N tests`, `collected N items`, and the runner's equivalent) with Grep or a bounded `tail`. Every major runner exits 0 when its filter matches zero tests -- `cargo test <filter>`, `pytest -k`, `go test -run`, `npm test -- <path>`, `dotnet test --filter` -- so the exit code alone cannot distinguish a genuine pass from a run that executed nothing.
3. Record `green_run` = `{cmd, exit, result, valid_green, log}`:
   - **Zero tests ran** for any target file -> `result: "INVALID"`, `valid_green: false`. NEVER record `PASSED` for a run that executed nothing: an implementation whose tests never ran is not verified.
   - Count parsed and > 0 for every target file -> `result: all target files passed ? "PASSED" : "FAILED"`, `valid_green: true`.
   - Count unparseable (unknown runner output shape) -> keep the exit-code result (`"PASSED"` / `"FAILED"`) and record `valid_green: null` -- the honest fallback. NEVER estimate or infer a count; the green-gate verifier judges the raw output, the same division of labour the invalid-red rule uses (mechanical exit/count from the orchestrator, semantic judgment from the verifier).
   - Budget expired -> `result: "TIMEOUT"`, `valid_green: null` (Gate discipline rule 2).
4. `captured_test_output` = a first line `GREEN GATE TEST COUNT: <count per target file, or "unparsed">` + one header line per green run.
5. The task's deterministic check is `PASS` on `PASSED`, `FAIL` on `FAILED` or `INVALID`, and `UNVERIFIABLE` on a `TIMEOUT` or `BUILD_FAILED`.

**Every gated task -> scoped checks.** After its red or green gate, run the single-file test command for each test file in the task's `verification_scope` that the gate above did not already run, into `$cycle_dir/gates/<task_id>-a<n>-scope-<k>.log`. For an impl task these must pass; for a test-author task, a scope file that passed at baseline must still pass. A scope failure makes the deterministic check `FAIL`. This is the task's regression net: it catches a task that breaks its neighbors at the task, where it is attributable and repairable, instead of at the end of the run.

**Standalone task (role: standalone or classic):** its `verification_scope` test files run as scoped checks when any exist; otherwise no gate runs and `captured_test_output` is `n/a`.

**Append evidence to the manifest `tdd.tasks` array** (one entry per testable task, keyed by `task_title`): `{task, test_files, red_run, green_run}`. The red_run is filled when the test-author task runs; green_run when the paired impl task runs (match by `tests_to_satisfy`).

**Invalid green (mirrors invalid red):** a green gate recorded `INVALID` / `valid_green: false` executed nothing, so the task is NOT treated as satisfied: its deterministic check is `FAIL`, the green-gate verifier reads the `GREEN GATE TEST COUNT` line in the gate evidence and flags the P1 `incorrect_implementation` bug (an exit-0 pass that ran zero tests), and 4e decides the repair. On a `valid_green: null` run the verifier makes the call from the raw log; the orchestrator never upgrades `null` to `true` on its own.

### 4d. Verify the task (independent, off the scheduler's critical path)

Every task attempt that produced a return gets exactly one independent semantic verifier -- verification is not configurable, because a task cannot integrate without a verdict. Print:

    [<task_id>] Committed <task_commit or "nothing">. Dispatching verification...

The verifier reads the task's own worktree at `task_commit`. That tree is already a pinned snapshot: nothing else writes to it while the verdict is pending, so the scheduler is free to start and advance other tasks meanwhile.

**Dispatch a semantic verifier** with the complete role definition (`../../agents/plan-verifier.md` relative to this skill, delivered by absolute path per **Portable role loading**) in the verifier prompt. Resolve its model per Step 1d-septies (role `verifier`; built-in default `sonnet` when available). The per-invocation prompt:

    You are being deployed as the task verifier for plan-runner cycle <cycle_n>.

    task_id: <task_id>
    attempt: <n>
    snapshot_root: <absolute task worktree path>
    base_commit: <base_commit>
    task_commit: <task_commit, or "none (no changes)">
    return_file: <absolute path: $cycle_dir/returns/<task_id>-a<n>-verifier.json>
    ownership_evidence: <absolute path: $cycle_dir/ownership/<task_id>-a<n>.txt> (conformance: <PASS | FAIL>)
    deterministic_checks: <PASS | FAIL | UNVERIFIABLE | n/a>
    baseline_state: <green | red | build_failed | timeout | n/a>

    ---
    agent_id: <task_id>-a<n>
    task_title: <task_title>
    acceptance_criteria:
    <acceptance_criteria as bulleted list>

    OWNED FILES (the dev agent was allowed to write these):
    <owned_files joined with newlines>
    SHARED FILES: <shared_files joined with newlines, or "none">
    VERIFICATION SCOPE: <verification_scope joined with newlines>

    DEV AGENT REPORTED:
    - status: <dev_status>
    - files_written: <dev's files_written joined with newlines>
    - files_unexpectedly_modified: <dev's files_unexpectedly_modified joined with newlines>
    - concerns: <dev's concerns joined with newlines>
    - role: <task role or "standalone">
    - tests_to_satisfy: <impl only: tests_to_satisfy joined with newlines, else "n/a">
    - captured_test_output: |
      <the 4c gate header lines for this task -- cmd, exit, result, test count, and each
       log's absolute path -- never the log text itself; or "n/a" when no gate ran>
    ---
    <on attempt 2 only:> PRIOR FINDINGS: <absolute path of the attempt-1 bug report> -- confirm each is resolved.

    FILE-BACKED RETURN: as your LAST action, write your bug-report JSON verbatim to
    return_file (create its returns/ directory if needed). The orchestrator reads that
    file as the source of truth for your verdict; your final message is a convenience
    preview of the same JSON. Write nothing else anywhere.

    Return only the JSON bug report, nothing else.

**Do NOT wait.** Persist status `verifying` (with `produced_commit` and the verifier's `return_file` among the task's verification artifacts), dispatch the verifier asynchronously, and return to the scheduling loop (4.0); the verdict is captured when its `return_file` appears. Its bounded wait is generous -- the verdict is file-backed, so poll for the file rather than inferring anything from task status; on the `teams` backend in particular, do NOT treat "no status update yet" as "no verdict", and never depend on a mailbox message or `TaskOutput` for it.

**No-self-verify rule (both backends, hard requirement):** The orchestrator MUST NOT perform the verification itself, MUST NOT substitute its own judgment for a verifier's report, and MUST NOT write a task's verdict artifacts from its own reading of the code. If the bounded wait genuinely expires without a report, do NOT self-verify to "rescue" the task: the missing verdict is recorded `UNVERIFIABLE`, which blocks integration and routes through the normal verify -> aggregate -> fix-plan -> re-run loop. A late or missing verdict becomes a tracked bug, never a silently-integrated task.

**Late-verdict reconciliation rule (both backends, hard requirement):** An expired bounded wait is not proof the verdict is dead -- a verifier that missed its wait may still deliver its report later. Recording `UNVERIFIABLE`, or dispatching a replacement verifier to keep the pipeline moving, does NOT close that task to a later verdict. If a verifier's report arrives after its task was recorded `UNVERIFIABLE`, or after a replacement verifier's verdict was already recorded for it, the orchestrator MUST reconcile rather than discard it: re-open that task's verdict capture, update `bugs/<task_id>.json` and its manifest entry, and record the supersession explicitly (e.g. a `superseded_by` / `reconciled_from` note in the bug JSON) rather than silently overwriting the history. Reconcile by UNION of findings: take the union of every verdict's `bugs` for that task attempt, and never let a later or replacement `CLEAN` verdict erase an earlier `BUGS_FOUND` -- a specific finding that cites a file and line is far more likely a true positive the other verifier missed than a fabrication. The orchestrator may confirm a late finding is grounded by checking that its cited file exists, but it MUST NOT adjudicate the disagreement by substituting its own judgment of whether the code is correct. A late verdict can never un-integrate a task; if it adds a P0 or P1 to a task that already integrated, the finding flows to the fix-plan and, if aggregation, the fix-plan, or the PR were already produced, they must be revised: re-run the Step 5.1 aggregation, and update an already-opened PR -- including returning it to draft when it was published as ready with a now-false zero-bug claim.

**Capture the verdict.** When the `return_file` appears, parse it (falling back to the verifier's returned message; if both fail, synthesize the `UNVERIFIABLE` report below), write it to `$cycle_dir/bugs/<task_id>.json`, adding the mechanical fields the scheduler owns so the report is self-contained evidence and validates as `../../schemas/bug-report.schema.json`'s task form -- `verification_scope` (from the graph), `ownership_evidence` (`{status, artifact_path, changed_paths}`, with one `{path, change_type, declared}` entry per line of the ownership artifact), and `deterministic_checks` (`{status, artifact_path}` naming the task's first gate log, or `null` when no gate ran); these are transcribed facts, never a judgment -- on attempt 2, replacing attempt 1's report after copying it to `bugs/<task_id>.a1.json`, which the aggregator ignores -- append a `task_verified` event, capture the verifier's token usage (its report carries a `token_usage` self-report as the fallback source; do not copy that field into the bug JSON), and tear the verifier down.

```json
{"task_id": "<task_id>", "agent_id": "<task_id>-a<n>", "task_title": "<task_title>", "verifier_status": "UNVERIFIABLE", "agent_statuses": {}, "bugs": [{"bug_id": "<task_id>-bug-1", "severity": "P2", "category": "incorrect_implementation", "title": "Task verifier returned no usable verdict", "file": "n/a", "line": null, "evidence": "<truncated raw output, or 'no report within the bounded wait'>", "expected": "Valid JSON bug report", "suggested_fix": "Re-run this task so the verifier produces a verdict"}]}
```

### 4e. Decide: integrate, repair once, or block

The decision is mechanical, made once per attempt from three durable facts: ownership conformance (4b), the deterministic check (4c), and the verdict (4d). A finding **blocks integration** when it is severity P0 or P1, when ownership conformance is `FAIL`, when the deterministic check is `FAIL`, or when the verdict is `UNVERIFIABLE`. An `UNVERIFIABLE` deterministic check blocks too -- except when `baseline_state` is `build_failed` or `timeout`: a gate that cannot build or finish on a codebase that could not build or finish before the run started is the codebase's pre-existing condition, not this task's failure. Record it in the task's evidence, do not block on it, and let the verdict and the final verification carry the judgment. (This is what lets a repair plan run against a codebase that does not compile yet.)

- **Nothing blocks** -> integrate (4f). P2 and P3 findings do not hold a task, or the subtree behind it, out of the branch: they ride along in `bugs/<task_id>.json`, reach the fix-plan, and keep the PR a draft. A quality nit must never cost every dependent task its turn.
- **Something blocks, and this was attempt 1** -> request exactly one evidence-backed repair attempt. Atomically persist status `retrying` with a `task_retry_requested` event naming the evidence, release the attempt's reservation (`paths_released`, `terminal_status: DISPOSED`), and in the same scheduler step -- before any other task is selected -- run 4a again for attempt 2 (its fresh reservation covers the same paths, so they are never up for grabs): in the SAME worktree on top of `task_commit`, or in a fresh worktree at the current integration commit when 4f requested a re-execution. A task gets ONE second attempt, whatever triggered it -- a repair, a stale-base re-execution, or a conflict rebuild share that budget (the schema caps `attempts` at 2). The repair dispatch is the task's normal role prompt plus:

      REPAIR ATTEMPT (2 of 2). Your previous attempt did not integrate. Read the findings and
      the gate logs they cite, fix every blocking finding within your owned files, and return as usual.
      findings: <absolute path of bugs/<task_id>.json>
      gate logs: <absolute paths of the attempt-1 logs whose result was not the expected one>

  A re-execution replaces that block with: `RE-EXECUTION (2 of 2). The branch changed underneath your task after you wrote it. Do the task again on the current code in this fresh worktree. what changed: <absolute path of the scoped stale-base diff or the conflict output>`.

  An `UNVERIFIABLE` verdict with no actionable finding is repaired by re-requesting verification of the same commit, not by re-dispatching the dev agent; that re-request is the task's one retry.
- **Something blocks, and this was attempt 2** -> the task is `blocked`. Persist the block reason and the evidence paths, append `task_blocked`, release the reservation (`terminal_status: BLOCKED`), leave its findings in `bugs/<task_id>.json` for the fix-plan, and record the outcome (4g). Never retry speculatively or erase prior evidence. Its dependents are blocked by step 1 of the next scheduler pass.

A dev agent that returned `BLOCKED` or `NEEDS_CONTEXT` produced a blocking P0 by the verifier's own rule (its step 1 covers both), so it follows the same path: one repair attempt -- with the agent's stated need in the findings -- then blocked.

### 4f. Central integration (serial)

Integration is the ONLY place the run-owned branch is mutated, it happens one task at a time, and it follows the protocol in `../../agents/plan-integrator.md`. The mechanical path needs no judgment, so the scheduler performs it directly in the integration worktree -- dispatching an agent for every integration would put a serialized LLM round trip behind every task in the run:

1. **Prerequisites.** Re-read the task state and require durable evidence of an eligible attempt (4e): ownership `PASS`; deterministic check `PASS` or `n/a` (or `UNVERIFIABLE` under 4e's unbuildable-baseline exception); a captured verdict with no blocking finding.
2. **Ownership, second check.** Re-run 4b's complete-diff comparison on `base_commit..task_commit` immediately before applying it. A mismatch with the first check is a block, not a retry.
3. **Stale base.** If the integration branch moved since `base_commit`, compare the intervening range (`git diff --name-only <base_commit>..<integration HEAD>`) with the task's `owned_files`, `shared_files`, and `verification_scope`. No intersection -> proceed. An intersection means the task was written and checked against code that has since changed underneath it: do not cherry-pick it. If this was attempt 1, request a re-execution in a new disposable worktree at the current integration commit (4e's repair path, with the scoped diff as its evidence); if attempt 2, block.
4. **Apply.** `git -C "<integration worktree>" cherry-pick <base_commit>..<task_commit>`. On success capture the resulting commit as `integrated_commit`; an empty range applies nothing, and its `integrated_commit` is the current integration HEAD. On a conflict, `git cherry-pick --abort`, save the conflict output to `$cycle_dir/ownership/<task_id>-a<n>-conflict.txt`, and dispatch the `plan-integrator` role (complete role definition by absolute path per **Portable role loading**; model per Step 1d-septies, role `integrator`) with `task_id`, `attempt`, `base_commit`, `task_commit`, the current `integration_commit`, the task's declared paths and `verification_scope`, the evidence paths, and `return_file: $cycle_dir/returns/<task_id>-integrator.json`. It has no shell and changes nothing: it returns `RETRY_REQUIRED` (spend the task's one second attempt on a re-execution at the current integration commit) or `BLOCKED`, and a `NEEDS_CONTEXT` or unparseable return is a `BLOCKED`. A task that already used its second attempt is blocked without asking. A second conflict marks the task `blocked`.

Never let a developer, test author, repair worker, or verifier apply a commit to the integration branch, and never apply one to the operator's branch.

### 4g. Record the outcome

Every terminal task passes through here -- integrated or blocked, including a dependency-derived block from 4.0 step 1 (which has no worktree, no attempts, and nothing to release). After a successful integration, increment `dag.integrations_completed`, persist the task's `integrated_commit` and status `integrated`, append `task_integrated`, then atomically persist that terminal transition together with a schema-valid `paths_released` event (`reservation_id`, `task_id`, `attempt`, `paths`, `terminal_status`, and `integration_commit`), releasing that attempt's reservation before its paths become dispatchable again -- the same release gate applies whenever an attempt is marked `BLOCKED` or its worktree is disposed, per `../../agents/plan-integrator.md` step 8 -- and then immediately re-evaluate the ready set (4.0). This permits a child of a fast integrated task to start while an unrelated slow task remains active.

Append or update the task's entry in the manifest `dag.tasks` array:

```json
{
  "task_id": "<id>", "required": true, "depends_on": ["<id>"], "status": "integrated | blocked", "attempts": <1|2>,
  "base_commit": "<sha>", "produced_commit": "<sha or null>", "integrated_commit": "<sha or null>",
  "verification_artifacts": ["<cycle-relative paths: bug report, ownership evidence, gate logs>"],
  "retry_evidence": ["<event ids or evidence paths for the repair or re-execution, if any>"],
  "block_reason": "<reason or null>", "lifecycle_event_ids": ["<event ids>"],
  "agent_source": "bundled | project:<name>", "dispatch_mechanism": "host_subagent | endpoint",
  "resolved_model": "<model>", "model_substituted": <object or null>,
  "bug_count": <n>, "duration_seconds": <dispatch through terminal state>,
  "tokens": {"input": <n|null>, "output": <n|null>, "total": <sum of this task's non-null agent totals, or null>}
}
```

`agent_source` is the value recorded at dispatch in 4a (`"bundled"` or `"project:<name>"`). `dispatch_mechanism` is `"endpoint"` for an agent dispatched by the HTTP endpoint dispatch step (4a), `"host_subagent"` for every subagent/teammate dispatch (bundled or project alike) -- both copied from the task-state map, never re-derived. Then print the task line:

```
[<task_id>] <INTEGRATED <sha7> | BLOCKED: <reason>>  attempts <n>  verifier <status>  bugs <n> (P0:<n> P1:<n> P2:<n> P3:<n>)  tokens <n or "n/a">  --  <integrated>/<T> integrated, <active> active, <ready> ready
```

Once the terminal state, its events, and its evidence are durable, remove the task's worktree and its disposable branch (unlink every shared directory first -- Step 1c-ter -- then `git worktree remove --force`, then `git branch -D`; on failure run `git worktree prune` and continue -- never fail the pipeline over cleanup). Durable returns, gate logs, ownership evidence, and bug reports stay in the cycle directory.

### 4h. Boundary suite (phase boundaries only)

At each non-terminal phase boundary, when `tdd_enabled`, run the FULL test command exactly once in the integration worktree, under **Gate discipline**, into `$cycle_dir/gates/suite-phase-<P>.log`, and compute with shell set operations the new failures: failing now, minus `tdd.baseline_failing` (the manifest's set, materialized to a sorted file -- the baseline of record, never a leftover log). A failing test that belongs to an **expected-red** file -- a test file owned by an integrated test-author task whose paired impl task is not yet integrated, read mechanically from the task graph and the task state -- is that test-author's red, not a regression. Write every other new failure, one per line, to `$cycle_dir/gates/suite-phase-<P>.regressions.txt`, record the result in the `checkpoint` event's `artifacts`, and report it in the phase summary. Do not dispatch anything for it: the per-task scoped checks are the attributable net, and the final verification (4j) is the one that gates delivery. Skip the boundary suite, and say so, when `baseline_state` is `timeout` -- a suite that cannot finish inside its budget would burn that budget at every boundary and still prove nothing. An unphased run has no boundary suite.

### 4i. Drain at a boundary

When `dag.integrations_completed` has advanced by `max_integrations_per_phase` in this session, stop selecting new tasks. Advance only the already-active task pipelines until each reaches a terminal state or a durable `retrying` state, run 4h, write a `checkpoint` event and set `dag.resume_task_id` to the next pending or ready task (or `null`), then return to Step 3-bis: a relay phase runner returns its phase-summary, and a stop-mode session prints the resume invocation. Do not count dispatches as integrations. No verdict may be left outstanding across a boundary without a durable `verifying` record that names its `return_file`.

### 4j. Final verification (once, after every task is terminal)

Before aggregation, when `tdd_enabled`, run the FULL test command once in the integration worktree, under **Gate discipline**, into `$cycle_dir/gates/final-suite.log`, and diff it against the baseline exactly as 4h does. Set the manifest `dag.final_verification`:

- `passed` -- the suite ran and no new failure remains outside expected reds (a blocked impl task leaves its test-author's reds expected).
- `failed` -- new failures remain; list the regressions file in `artifacts`. Each regression becomes one P0 `broken_existing` bug in `$cycle_dir/bugs/final-suite.json`, attributed mechanically to the integrated task whose `owned_files` or `verification_scope` contains the failing test's file, or unattributed when none does. The file has the shape of any other report -- `{"task_id": "final-suite", "agent_id": "final-suite", "task_title": "Final full-suite verification", "verifier_status": "BUGS_FOUND", "agent_statuses": {}, "bugs": [...]}`, with `bug_id`s of the form `final-suite-bug-<N>`. These bugs are relayed from the gate's own output, not a judgment of code, so they do not violate the no-self-verify rule.
- `unverifiable` -- the suite did not run (`BUILD_FAILED`) or did not finish (`TIMEOUT`); never recorded as a pass.

Append a `final_verification` event with the log and regressions paths. When `tdd_enabled` is false there is no suite to run: record `passed` with an `artifacts` note that no test command exists, since ownership conformance and independent verification are the only gates a classic run has. Then unlink its shared directories and remove the integration worktree (the run-owned branch stays: it is the PR source) and proceed to Step 5.

## Step 5: AGGREGATE

Step 5 runs **once**, after every task is terminal and the final verification (4j) has recorded its result: in the unphased session, in the relay driver after its last phase runner returns, or in the terminal stop-mode session. Aggregation reads every task's bug report from disk, so it needs no context from any scheduler session.

### 5.0. Verifier-coverage gate (runs before counting, on every path)

Before counting bugs, assert that **every** graph task has a verdict on disk or a durable reason it never needed one. For each task in `task-graph.json`:

- status `integrated`, or `blocked` after at least one attempt -> `$cycle_dir/bugs/<task_id>.json` MUST exist and parse with a non-null `verifier_status`.
- status `blocked` with zero attempts (a dependency-derived block: it was never dispatched) -> it needs no verdict; synthesize its report so the block reaches the fix-plan: `{"task_id": "<id>", "agent_id": "<id>-a0", "task_title": "<task_title>", "verifier_status": "BUGS_FOUND", "agent_statuses": {}, "bugs": [{"bug_id": "<id>-bug-1", "severity": "P0", "category": "missing_requirement", "title": "Task never ran: blocked dependency <dep task_id>", "file": "<owned_files[0]>", "line": null, "evidence": "Dependency <dep task_id> was blocked, so this task was never dispatched.", "expected": "Task completes all acceptance criteria", "suggested_fix": "Fix <dep task_id> first, then run this task"}]}`. This relays the scheduler's own durable state, not a judgment of code.
- status `blocked` whose report carries no P0 or P1 finding (a mechanical block: a failed check under a clean verdict, a stale base, a second conflict) -> append one P0 `missing_requirement` bug to its report, `"title": "Task blocked: <block_reason>"`, with the block's evidence path as `evidence`, and set `verifier_status` to `BUGS_FOUND`. Like the dependency-derived block above, this relays the scheduler's own durable state. A blocked task with no bug would vanish from the fix-plan, and the run would report zero bugs with work missing from the branch.
- any other status means the scheduler did not finish: STOP and offer the resume invocation -- never aggregate over a task that is still in flight.

If a task that ran has no bug report, or one with a null `verifier_status`, its verifier never landed -- the task must not be treated as clean. Synthesize and write:

```json
{"task_id": "<task_id>", "agent_id": "<task_id>-a<last attempt>", "task_title": "<task_title>", "verifier_status": "UNVERIFIABLE", "agent_statuses": {}, "bugs": [{"bug_id": "<task_id>-bug-1", "severity": "P2", "category": "incorrect_implementation", "title": "Task <task_id> verifier verdict missing -- task closed without verification", "file": "n/a", "line": null, "evidence": "No bugs/<task_id>.json with a verifier_status was found at aggregation time.", "expected": "Every task is gated by its verifier before the cycle closes", "suggested_fix": "Re-run this task so the verifier produces a verdict"}]}
```

Print a warning naming each backfilled task. An `integrated` task can never need this backfill by construction (4f requires a captured verdict), so a backfilled integrated task also means the state was tampered with or corrupted: say so. This gate makes it structurally impossible to reach the PR step (Step 8, downstream of Step 5 on both the clean and buggy paths) while a verifier verdict for any task is still outstanding. A backfilled `UNVERIFIABLE` is still a placeholder, not a closed book: if that task's real verifier report shows up later -- even after this gate ran, after aggregation, or after a PR was opened -- it is a late verdict and MUST be reconciled per the late-verdict reconciliation rule (4d), never discarded because the gate already moved on.

### 5.1. Count and aggregate

Count total bugs across `$cycle_dir/bugs/*.json` (ignoring superseded `*.a1.json` reports). Finalize the token tally from the manifest's durable `token_usage.by_agent` (see **Token accounting**): `total_tokens` = the sum of every **non-null** per-agent `total`; `agents_total` = the count of entries; `agents_reported` = the count of entries whose `total` is non-null; `complete` = `agents_reported == agents_total`. An agent left `null` stays excluded from the sums and is never rescued with a guess; when `complete` is false the total is a lower bound.

If total bugs == 0:

```

Update the manifest: `total_bugs: 0`, `token_usage: <finalized tally>`, `completed_at: <ISO timestamp>`. Run 5.2 and skip to Step 7 (final summary).

If total bugs > 0:

```

```

Dispatch one foreground aggregator with the complete role definition (`../../agents/plan-aggregator.md` relative to this skill, delivered by absolute path per **Portable role loading**) and these per-invocation parameters. Resolve its model per Step 1d-septies (role `aggregator`; built-in default `sonnet` when available):

```

cycle_dir: <absolute path to $cycle_dir>
input_plan: <absolute path to the original plan>

Read all of this cycle's bug JSONs: <cycle_dir>/bugs/*.json (skip superseded *.a1.json files).
Read the task graph at <cycle_dir>/task-graph.json for task context, and the task outcomes
(integrated / blocked, with block reasons) in <cycle_dir>/manifest.json under dag.tasks.

```

The aggregator writes the two files itself. When it returns, parse its status JSON. Capture the aggregator's token usage (see **Token accounting**; its status JSON carries a `token_usage` self-report as the fallback source), append it to `token_usage.by_agent` as `{"agent": "aggregator", "phase": "aggregate", ...}`, and re-finalize the tally.

Run 5.2, then skip to Step 7-bis with `total_bugs = <count>`, `next_cycle_plan = null`.

Update manifest:

- `token_usage: <finalized tally>`
- `next_cycle_plan: <fix-plan path from aggregator>`
- `completed_at: <ISO timestamp>`

Then run 5.2 and proceed to Step 6.

### 5.2. Complete the run-state

Run this at the end of Step 5 on **every** path (zero-bug, bugs-found, and aggregator-failure), before routing to Step 6 or Step 7. Set the run-state (`$cycle_dir/run-state.json`) `overall_status` to `complete`, rewrite `updated_at`, and write it back. This is the single point where a cycle's run-state reaches `complete`, and it fires on every terminal path -- clean, bugs-found `Y` handoff (the fix-plan re-run is a separate new cycle with its own run-state), and bugs-found `n`. A `complete` run-state is never re-offered or resumed by pre-flight auto-detect (Resume step R.1). There is nothing to roll up: the cycle has one manifest, and every scheduler session wrote to it.

If cycle_n > 1, add a convergence hint:

Then prompt:

[Y] = auto-handoff to a fresh-context subagent running the Plan Runner run skill on <fix-plan.md>
[n] = stop here (you can resume later with the same skill invocation)

(Y/n)
```

A fix-plan re-run is a normal run through this same pipeline and **inherits phasing automatically, by the same rules -- no special-casing.** It analyzes `fix-plan.md` into its own task graph and writes its own per-cycle run-state. The one thing it must be told is where this cycle's work lives: this cycle integrated onto its run-owned branch and never touched the operator's checkout, so a re-run based on the operator's `HEAD` would be fixing code that is not there. The re-run therefore bases its own run-owned branch on THIS cycle's integration branch, via the internal `--base <ref>` input: Step 1c uses that ref as `base_ref` instead of `HEAD` and skips the dirty-checkout prompt (nothing is read from the operator's working tree). The final cycle's branch thus carries every cycle's integrated work, and the single PR opened at the end delivers all of it.

If `n`: print `Stopping fix-plan re-run. Proceeding to the PR step.` Proceed to Step 7-bis.

## Step 8: OPEN PR
